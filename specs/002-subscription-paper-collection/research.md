# Phase 0 Research: Subscription-Based Paper Collection

All `[NEEDS CLARIFICATION]` items from the spec were already resolved during `/speckit-clarify` (see `spec.md` § Clarifications: first-collection window, provider routing, scheduling mechanism, identity matching, `sourceId` normalization). The research below covers the remaining *technical* decisions needed to turn those resolved business rules into a concrete design against this repo's actual `src/models/` types (001) and the Obsidian plugin platform.

## 1. Making network calls from an Obsidian plugin

**Decision**: Use Obsidian's `requestUrl(options)` (exported by the `obsidian` package) for both the arXiv and Semantic Scholar HTTP calls, never the global `fetch` or a Node HTTP client.

**Rationale**: `requestUrl` is Obsidian's own cross-platform HTTP primitive — it works unchanged on desktop and mobile and, critically, is not subject to the CORS restrictions that block a plain `fetch` call to most third-party APIs from within Obsidian's renderer. Node's `http`/`https` modules would violate constitution Principle I (mobile-compatible-by-default; Node/Electron-only APIs require `isDesktopOnly`), which this feature has no reason to set.

**Alternatives considered**:
- *Global `fetch`*: rejected — frequently blocked by CORS inside Obsidian's Electron/Capacitor webview for arbitrary third-party origins; `requestUrl` exists specifically to route around this.
- *Node `https` module*: rejected — desktop-only, forces `isDesktopOnly: true` on the whole plugin, contradicting the mobile-compatibility goal already established by 001/the constitution.

## 2. Parsing arXiv's Atom XML response

**Decision**: Parse the raw XML string returned by `requestUrl` with the standard `DOMParser` (`new DOMParser().parseFromString(xml, 'application/xml')`), then walk `<entry>` elements to build one `PaperCandidate` per entry (title, authors from repeated `<author><name>`, publication year from `<published>`, abstract from `<summary>`, `sourceId` built from the arXiv id URL, `citationCount`/`references` left `undefined`). Exported as two functions (corrected 2026-07-06 — see Decision 25): `parseArxivEntry(entry: Element): PaperCandidate` does the actual per-entry mapping; `parseArxivAtom(xml: string): PaperCandidate[]` is a thin convenience wrapper that parses a whole document and maps every entry through `parseArxivEntry`.

**Rationale**: `DOMParser` is a standard Web API available in both the desktop (Chromium/Electron) and mobile (Capacitor WebView) Obsidian runtimes — no new dependency, and it handles Atom's XML namespaces and repeated-element structure (multiple `<author>` per `<entry>`) more robustly than regex/string scanning. This keeps the parser file free of any XML library dependency, matching 001's "no new runtime dependency" precedent.

**Alternatives considered**:
- *A dedicated XML/Atom parsing npm package (e.g. `fast-xml-parser`)*: rejected for v1 — adds a bundled dependency for a format `DOMParser` already handles natively; revisit only if `DOMParser`'s namespace handling proves insufficient in practice.
- *Regex-based extraction*: rejected — Atom entries have nested/repeated elements (multiple authors, multiple links) that regex handles unreliably compared to real DOM traversal.

## 3. Parsing Semantic Scholar's JSON response

**Decision**: `requestUrl`'s response body is parsed with `JSON.parse` (or Obsidian's already-parsed `.json` accessor) directly into a typed intermediate shape, then mapped into the citation fields (`citationCount`, `references` with each reference's `sourceId` normalized per Decision 7 below) merged onto an existing `PaperCandidate` during enrichment, or into a fresh one if Semantic Scholar is ever used to build a candidate from scratch (not needed under the "arXiv-only discovery" clarification, but the mapping function stays provider-agnostic so it isn't wasted if that changes later).

**Rationale**: JSON needs no special parsing library; the only design decision is keeping the field-mapping (Semantic Scholar's `paperId`/`citationCount`/`references[].externalIds.ArXiv` etc.) isolated in its own module (`semanticScholarParser.ts`) so a future Semantic Scholar API schema change touches one file.

**Alternatives considered**: None materially different — this is a standard JSON-to-typed-object mapping with no ambiguity worth exploring alternatives for.

## 4. Scheduling per-subscription checks without leaking timers

**Decision**: A `scheduler.ts` module exposes `startScheduler(plugin: Plugin, deps: SchedulerDeps)` (contracts § scheduler.ts — `deps.getSubscriptions`/`deps.runCheck`/etc.) and relies entirely on `plugin.registerInterval(window.setInterval(...))` for the recurring tick — firing every **15 minutes**, a single coarse interval that on each tick checks which enabled subscriptions are now due, rather than one JS timer per subscription. `onload` calls `startScheduler(...)` once; because it is registered via `registerInterval`, `onunload` cleanup is automatic and requires no explicit `stop()` bookkeeping.

**Rationale**: Constitution Principle II (NON-NEGOTIABLE) prohibits raw `setInterval` outside `this.registerInterval(...)`. A single coarse recurring tick that re-evaluates all subscriptions' due-times is simpler and leak-proof compared to creating/destroying one OS/JS timer per subscription as subscriptions are added, deleted, or have their interval changed — that approach would require careful teardown bookkeeping (a map of subscription id → timer handle, cleared on delete/interval-change) that is easy to get subtly wrong. The "per-subscription timer" language in the spec's clarification refers to each subscription tracking its *own next-check time* (derived from its own `checkIntervalHours` and `lastCheckedAt`), not to one OS timer object per subscription — a single tick loop that compares "is `now >= lastCheckedAt + checkIntervalHours` for this subscription" achieves exactly that independence of cadence with one registered interval to clean up. **15 minutes** (pinned 2026-07-06, superseding the earlier "every few minutes" placeholder) is chosen because the allowed check intervals are whole hours (6/12/24/48/72) — a 15-minute polling granularity bounds how late a due check can fire to at most ~15 minutes past its exact due time, under 4% of even the shortest allowed interval, while not waking the plugin needlessly often on mobile/battery-constrained devices.

**Alternatives considered**:
- *One `registerInterval` per subscription*: rejected — every subscription add/delete/interval-change would need to create/clear its own timer handle, multiplying the surface for a lifecycle leak that Principle II explicitly calls out as NON-NEGOTIABLE; a single recurring tick sidesteps this entirely.
- *`setTimeout` chains re-armed after each check*: rejected — same per-subscription teardown bookkeeping problem, plus `setTimeout` still needs the same `register*` wrapper treatment and gains nothing over one shared interval.
- *A shorter tick (e.g. 1-5 minutes)*: rejected — no measurable benefit given hour-granularity check intervals, at the cost of waking the plugin roughly 3-15x more often for no user-visible improvement in promptness.
- *A longer tick (e.g. 1 hour)*: rejected — would let a due check slip by up to an hour past its due time, a visible fraction (up to ~17%) of the shortest allowed 6-hour interval.

## 5. Catch-up-on-load computation

**Decision**: On `onload`, before starting the recurring tick, the scheduler runs one pass over all enabled subscriptions: for each, if `lastCheckedAt` is not null, the catch-up window is `[lastCheckedAt, now]`; if `lastCheckedAt` is null (brand-new subscription), the window is `[now - 24h, now]` per the clarified first-collection default. Each subscription's catch-up search reuses the exact same "check" code path as a normal scheduled tick (same provider query, same candidate/enrichment/promotion/dedupe/batch pipeline), parameterized only by the window bounds — there is no separate "catch-up" implementation to keep in sync with the "live tick" implementation.

**Rationale**: Directly implements FR-004 or the *equivalent* case at plugin start, keeps `scheduler.ts` as the single owner of "when do we check and over what window" (FR-006's "advance `lastCheckedAt` only over the window actually searched" is easiest to get right with one code path), and satisfies the first-collection-window clarification without a second, divergent implementation.

**Alternatives considered**: A separate one-shot "catch-up service" module distinct from the scheduler's tick handler — rejected as needless duplication; the window-bounds parameterization already covers both cases from one function.

## 6. Sequential, non-freezing batch processing

**Decision** (implemented inside `pipeline.ts`'s `runCollectionPass`, not a separate `batchQueue.ts` — corrected in analysis review; see amended Decision 31): a batch of discovered provider entries is processed one at a time using `for (const entry of batch) { await processOne(entry); }`, where `processOne` is itself `async` (network calls for enrichment are naturally awaited) and — for a purely-CPU-bound stretch with no natural `await` (e.g. many `PaperCandidate`s already in memory with citation data, so no further network call is needed before promotion) — the loop yields to the event loop between items via `await new Promise(resolve => setTimeout(resolve, 0))` so a large batch can't block Obsidian's UI thread in one synchronous tick.

**Rationale**: Directly implements FR-013/Edge Cases ("processed sequentially without freezing the interface"). `async`/`await` in a `for...of` loop is the simplest construct that is both sequential (papers are handed to 003/004 one at a time — no accidental concurrent double-persist of the same paper) and non-blocking (each iteration returns control to the event loop), with the explicit zero-delay `setTimeout` yield covering the edge case where an item's processing has no `await` of its own.

**Alternatives considered**:
- *`Promise.all` over the whole batch*: rejected — the spec's "processed sequentially" language and FR-013 explicitly call for one-at-a-time, non-concurrent handling (also avoids simultaneously blasting the persistence layer with concurrent writes for papers that could collide on filenames).
- *A Web Worker*: rejected as unnecessary complexity — none of the per-paper work is CPU-heavy enough (XML/JSON parsing of one entry, a couple of network calls) to need moving off the main thread; a worker would also complicate `requestUrl` usage (an Obsidian API, not necessarily available identically inside a worker context) for no measurable benefit.

## 7. Citation enrichment: identity matching and termination

**Decision**: `enrichment.ts` matches a candidate to its Semantic Scholar record **by arXiv ID only** (`GET /graph/v1/paper/ARXIV:<id>`), which Semantic Scholar's API supports directly. There is **no title/author fallback**. A `404` (no record for that arXiv ID) is classified as a **terminal absence** — enrichment stops for that paper on this pass, `citationsKnown` stays `false`, and it is not retried by this feature again (only 005's manual refresh or a future auto-heal may retry it later, per FR-018). A genuine transient failure (network error, 5xx, rate-limit/`429` response) is retried up to a small bounded count (3 attempts, 3-second spacing) within the same pass before falling through to the same `citationsKnown = false` outcome.

**Rationale (revised 2026-07-06, spec Clarification session 2026-07-06)**: An earlier version of this decision fell back to a title+first-author search when the arXiv-ID lookup found no match. That fallback was removed because a title/author relevance search can rank an unrelated paper by an author with a common surname above the correct one, and accepting that top result would silently attach the *wrong* paper's citation count/references — a worse outcome than the correct one (an honest `citationsKnown = false`) that the fallback was meant to avoid. Matching by arXiv ID only accepts a higher terminal-absence rate (a real, recent arXiv paper simply not yet indexed by Semantic Scholar) in exchange for zero risk of a false-positive match silently corrupting citation data.

**Alternatives considered**:
- *DOI-based matching*: rejected as primary — arXiv preprints frequently lack a registered DOI at collection time; arXiv-ID matching is more universally available for this feature's actual inputs (arXiv-discovered candidates).
- *Unbounded retry until success*: rejected — directly contradicts FR-018's explicit bounded-retry requirement and would risk an unresponsive provider stalling collection indefinitely.
- *Keep the title+author fallback but require a higher-confidence match (e.g. exact title string match, not just top relevance result)*: considered, but still not zero-risk (two distinct papers can legitimately share a title), and adds meaningful implementation complexity for a benefit (fewer terminal-absence outcomes) that this project decided not to trade safety for.

## 8. Deduplication across subscriptions and overlapping windows

**Decision**: A single per-`runCheck`-invocation (and per-catch-up-pass) `Set<PaperSourceId>` is threaded through `dedupe.ts`: before a discovered entry is handed to the enrichment/promotion pipeline, its `sourceId` is checked against (a) the in-memory set for entries already processed in this same collection run, and (b) a hand-off hook to 003 for "does a record with this `sourceId` already exist in the persisted store" (needed because two *different* scheduled ticks, not just two subscriptions in the same tick, can discover the same already-stored paper). Either match short-circuits further processing for that entry.

**Rationale**: FR-009/SC-004 require exactly-once processing regardless of whether the duplicate arises from two subscriptions in the same run or overlapping catch-up windows across separate runs. Checking only the in-memory set would miss the cross-run case (e.g., paper already collected and stored last week resurfacing under a different subscription's catch-up window); checking only the persisted store on every entry would be correct but this feature does no file I/O itself (spec Out of Scope) — so the "already persisted" check is a narrow read-only hook into 003, not a re-implementation of 003's storage.

**Alternatives considered**: Rely solely on 003 rejecting a duplicate write — rejected because that still means this feature would run enrichment (network calls) and possibly summarization (004) needlessly for a paper it's about to discard, wasting a Semantic Scholar call and an LLM call that FR-009's "processed only once" is meant to avoid, not just "stored once."

## 9. `sourceId` normalization for enrichment-supplied references

**Decision**: When Semantic Scholar enrichment returns a paper's references/citations, each reference is mapped to a `PaperSourceId` (001's `arxiv:<id>` / `semanticScholar:<id>` template-literal type) by checking the reference's `externalIds.ArXiv` field first; if present, the reference's `sourceId` is `arxiv:<baseId>` where `baseId` has any trailing `vN` version suffix stripped — **the exact same stripping rule `arxivParser.ts` applies to a directly-collected paper's own `sourceId` (Decision 13)**, applied here to `semanticScholarParser.ts`'s output too. Only when no arXiv ID is present does the reference keep a `semanticScholar:<paperId>` identifier.

**Rationale**: Directly implements the clarified `sourceId`-normalization answer, and keeps enrichment-sourced references compatible with 001's existing `PaperSourceId` type with zero changes to that type — this feature is purely a consumer/producer of values already shaped by 001. The version-stripping consistency matters beyond tidiness: graph edges (006) connect papers by **exact `sourceId` string equality** (A→B when A's `references` includes B's `sourceId`). If a directly-collected paper's `sourceId` is version-stripped (`arxiv:2301.12345`) but a *reference to that same paper*, arriving via Semantic Scholar's `externalIds.ArXiv`, were left un-stripped (`arxiv:2301.12345v1`), the two strings would never match — 006 would silently fail to draw an edge between two nodes that are, in fact, the same paper. Applying Decision 13's stripping rule uniformly to every arXiv-ID-derived `sourceId` this feature produces, regardless of which parser produced it, is what keeps that guarantee actually true rather than true-by-accident for only one of the two paths that build `arxiv:`-scheme `sourceId`s.

**Alternatives considered**:
- Always keep `semanticScholar:` scheme regardless of arXiv-ID availability: rejected per the clarification answer, since it would prevent graph edges (006) from connecting a Semantic-Scholar-supplied reference to the same paper when it was (or later is) independently collected via arXiv under an `arxiv:` id.
- Strip the version only in `arxivParser.ts` and assume Semantic Scholar's `externalIds.ArXiv` never carries one: rejected — this is an unverified assumption about a third-party field's format, and the cost of stripping defensively in both places is one shared helper function call, not a meaningful implementation burden.

## 10. Pipeline hand-off to 003 (persistence) and 004 (summarization)

**Decision**: `pipeline.ts` accepts two injected async callbacks at construction/wiring time — `summarize?: (input: SummarizationInput) => Promise<SummaryResult | undefined>` and `persist: (paper: Paper, summary?: SummaryResult) => Promise<void>` (see Decision 22 for `SummarizationInput`/`SummaryResult`) — rather than importing 003/004 modules directly. `main.ts` (or a small composition point) supplies the real 003/004 implementations once those features exist; until then, tests/quickstart can supply stub callbacks.

**Rationale**: FR-017 requires this feature to *sequence* enrichment → summarization → persistence without *implementing* summarization or file I/O. Dependency injection via callback parameters (rather than direct imports of `src/notes/...` or `src/summarization/...` modules that don't exist yet) lets 002 be implemented, and its pipeline logic unit-verified, independently of 003/004's implementation status — matching this repo's incremental, spec-numbered build order. A summarization failure (callback throws or times out) is caught by `pipeline.ts` and treated as "no summary produced" — `persist` is still called, with its `summary` argument simply omitted, falling through to persistence with the paper's plain abstract, per FR-017's "summarization failure MUST NOT block persistence." **`persist` carrying a `summary` argument is not optional plumbing — it is the only path 004's generated text can reach 003 through**; an earlier draft of this contract had `persist(paper: Paper)` with no way to receive `summarize`'s result at all, which would have silently discarded every generated summary (corrected 2026-07-06, see Decision 22).

**Alternatives considered**: Direct static imports of 003/004 modules — rejected for now since those modules don't exist yet in this repository; revisit once 003/004 land (likely a mechanical swap from injected callbacks to direct calls, or keeping the injection seam for testability).

## 11. arXiv query construction, date-range windowing, and pagination

**Decision**: `queryArxiv` builds a `search_query` combining the subscription's own term with a `submittedDate` range clause via `AND`, per arXiv's documented syntax:
- `keyword` → `` all:"<value>" AND submittedDate:[<from> TO <to>] ``
- `author` → `` au:"<value>" AND submittedDate:[<from> TO <to>] ``
- `arxivCategory` → `` cat:<value> AND submittedDate:[<from> TO <to>] ``

where `<from>`/`<to>` are the `CollectionWindow` bounds formatted as arXiv's `YYYYMMDDTTTT` (GMT). **Amended by Decision 32**: the query MUST also pin `&sortBy=submittedDate&sortOrder=ascending` (never arXiv's default relevance sort), and `queryArxiv` additionally returns a `coveredThrough` timestamp so a truncated window advances `lastCheckedAt` only over the portion actually covered — see Decision 32. Results are paged with `start`/`max_results` (0-based `start`, `max_results = 100` per page — well under arXiv's own 2000-per-call ceiling and its "refine queries returning more than 1,000 results" guidance) until arXiv returns fewer than `max_results` entries for that page (window fully covered) or a safety cap of **10 pages / 1,000 entries** is hit for a single subscription's single check. Hitting the cap sets `truncated: true` (reusing the FR-014 mechanism — no separate signal is introduced) and stops paging rather than continuing indefinitely. A fixed **3-second delay** is inserted between successive page requests for the *same* subscription's query, per arXiv's own rate-limit guidance ("we encourage you to play nice and incorporate a 3 second delay").

**Rationale**: arXiv's API documentation is explicit about all three of these (pagination parameters, a documented per-call/total ceiling, and a requested inter-request delay) — this is not a judgment call but a direct transcription of the provider's stated contract, needed before `arxivClient.ts` can be implemented at all. Capping at 1,000 entries (not arXiv's own 2,000/30,000 ceiling) matches arXiv's *own* recommendation to keep individual queries under 1,000 results, and keeps a single pathological subscription (e.g., a very broad category right after registration, or a long off-period catch-up) from taking many minutes and dozens of sequential requests before this feature's own batch-processing loop (Decision 6, implemented in `pipeline.ts`) even starts processing candidates.

**Alternatives considered**:
- *A single `max_results` request per check, no pagination loop*: rejected — a catch-up window after a long off-period, or a broad category subscription, can plausibly exceed arXiv's default/requested page size; silently truncating to one page without setting `truncated: true` would violate FR-014 (user must be informed when a window isn't fully covered).
- *No safety cap (page until arXiv returns nothing new)*: rejected — arXiv's own documentation warns a 30,000-result query "will typically take a little over 2 minutes to return," which would stall a single subscription's check well past what FR-013's "no freezing" spirit intends, and needlessly hammers a third-party API section that explicitly asks callers to self-limit.
- *No inter-page delay*: rejected — directly contradicts arXiv's own stated rate-limit ask; a 3-second delay across at most 10 pages adds at most ~30 seconds to the rare worst-case check, not the common case (most subscriptions' windows return far fewer than 100 results and never page at all).

## 12. Semantic Scholar endpoint shape and rate-limit posture

**Decision** (**collection path amended by Decision 33** — 002's collection now enriches via the `POST /paper/batch` endpoint, not this single-paper `GET`; the single-paper `fetchSemanticScholarPaper` described here is retained only for 005's per-paper manual refresh): `fetchSemanticScholarPaper` calls exactly one endpoint — `GET /graph/v1/paper/ARXIV:<arxivId>?fields=citationCount,references.paperId,references.externalIds` (research.md Decision 7's arXiv-ID-only match; no title/author search endpoint is called at all), adding an `x-api-key` header carrying `PluginSettings.semanticScholarApiKey` whenever that optional setting is present (Clarification 2026-07-06, FR-020). A **404** response is mapped directly to `EnrichmentOutcome.status === 'terminalAbsence'` (the paper genuinely isn't in Semantic Scholar's index — matches Decision 7's "positive no-such-paper" case exactly). A **429** (rate-limited) or network-level failure is mapped to a transient-retry attempt (bounded to 3, per Decision 7), with the same 3-second inter-attempt spacing used for arXiv's own pagination (Decision 11) as a conservative default when no API key is configured.

**Rationale**: The 404/429 mapping requires no invented behavior — it follows directly from Semantic Scholar's documented status codes and this feature's own already-decided terminal-vs-transient split (Decision 7); the only new information this research contributes is *which* HTTP status maps to *which* of the two existing `EnrichmentOutcome` branches, so `enrichment.ts` has an unambiguous mapping to implement. Calling only the single-paper-lookup endpoint (never `/paper/search`) is a direct consequence of Decision 7's 2026-07-06 revision to drop the title/author fallback — there is simply no second endpoint for this client to call. An optional API key is supported as an **always-available** setting (not gated behind "only if unauthenticated access proves insufficient") because: it costs nothing when absent (the header is simply omitted, behavior is identical to today), it's a one-line addition to the request given the key is already read from `PluginSettings`, and it gives a user who registers many subscriptions a documented, dedicated rate limit instead of sharing an undocumented, worldwide unauthenticated pool — there's no reason to make that user wait for a future feature when the plumbing is this cheap now.

**Alternatives considered**:
- *No API key support at all, unauthenticated-only*: rejected (revised 2026-07-06) — the original reasoning ("unauthenticated access is sufficient for this feature's low call volume") is still true on average, but it doesn't help the user who registers many subscriptions and *does* hit the shared pool's limits; supporting an optional key costs nothing for users who don't set one, so there's no reason to withhold it.
- *Require an API key*: rejected — would break constitution Principle IV's "no required setup before other features can work" posture and 001/002's "concrete, usable default with no setup" precedent; the key is an optional performance/reliability upgrade, never a prerequisite for enrichment to function.
- *Treat 429 as terminal (stop retrying immediately)*: rejected — a rate-limit response is definitionally transient (the same request would very plausibly succeed moments later), and FR-018 explicitly requires bounded retry for transient failures, only treating a positive absence/unresolved-match as terminal.

## 13. Stripping the arXiv version suffix from `sourceId`

**Decision**: `arxivParser.ts` extracts the base arXiv identifier from the Atom `<id>` element (e.g. `http://arxiv.org/abs/2301.12345v2` → `2301.12345`) by stripping a trailing `vN` version suffix before building `sourceId` as `` `arxiv:${baseId}` ``. `sourceId` therefore never carries a version number.

**Rationale (spec Clarification session 2026-07-06)**: arXiv preprints are frequently revised, and each revision is served under the same base ID with an incrementing version suffix. If `sourceId` included the version, revising a paper would make it look like a brand-new paper to this feature's own dedup (FR-009) and to 003's persisted-store lookup, causing the same underlying paper to be collected (and noted) again every time its author posts a revision. Stripping the version keeps `sourceId` stable across revisions, which is what FR-009/SC-004's "processed only once" is meant to guarantee — a revision is not a new paper for this feature's purposes.

**Consequence, explicitly accepted as out of scope**: because a revision reuses the same `sourceId`, `dedupe.ts`'s `alreadyPersisted` check (Decision 8) will treat a paper's later revision as already collected and skip it — this feature does not re-fetch or update an already-persisted paper's title/abstract/authors when arXiv serves a newer version. Refreshing stored content to match a newer revision is a distinct concern from collection and is left to a future feature (analogous to how citation re-enrichment was deferred; see `specs-futureworks/010-automatic-citation-refresh`), not solved here.

**Alternatives considered**:
- *Keep the version in `sourceId`, dedup on the base ID separately*: rejected — this reintroduces exactly the two-different-identifiers-for-one-paper problem `sourceId` (001 FR-015) exists to prevent, and every consumer of `sourceId` (003, 006) would need its own version-stripping logic instead of this feature fixing it once at the source.
- *Track the arXiv version number as a separate field on `Paper` for future refresh use*: deferred — no current feature (002–008) reads such a field; adding it now would be speculative, unused surface area (contradicts the project's "don't design for hypothetical requirements" convention). Revisit only if a future refresh/re-sync feature is actually proposed.

## 14. Preventing a subscription from being checked twice concurrently

**Decision**: `scheduler.ts` keeps an in-memory `Set<string>` of subscriptions whose `runCheck` is currently in flight, keyed by `` `${subscription.type}:${subscription.value}` `` — **not** by object reference. Before invoking `runCheck` for a subscription — whether from the catch-up pass or a recurring tick — the scheduler skips it if its key is already in that set; otherwise it adds the key, invokes `runCheck`, and removes the key once `runCheck` settles (resolves or rejects).

**Rationale (spec Clarification session 2026-07-06)**: The catch-up pass (Decision 5) and the recurring tick (Decision 4) are two distinct call sites that both eventually invoke the same per-subscription `runCheck`. A catch-up pass covering a long off-period window (large batch, Decision 6's sequential processing) can plausibly still be running when the first recurring tick becomes due, especially for a subscription with a short check interval. Without a guard, both call sites could invoke `runCheck` for the same subscription at the same time, double-processing its window and risking two concurrent `recordChecked` calls racing each other. A skipped subscription loses nothing — its `lastCheckedAt` has not advanced, so it remains due and is simply picked up on the very next opportunity (the tick after this one, or the next load).

**Why a string key, not the `Subscription` object itself**: `SchedulerDeps.getSubscriptions()` (contracts) has no guarantee it returns the same object identity on every call — `subscriptionStore.list()` (data-model.md) may reasonably return a fresh array/copy each time it's called, which is exactly what a catch-up pass and a later tick would do (two separate `getSubscriptions()` calls). A `Set<Subscription>` keyed by object reference would then silently fail to recognize "the same subscription" across those two calls, defeating the whole guard. `type`+`value` is a subscription's natural identity for this purpose — 001 does not define a stable id field, but a given type+value pair is what the user actually registered and is stable across `list()` calls even if the wrapping object is not.

**Alternatives considered**:
- *`Set<Subscription>` keyed by object reference (original draft)*: rejected after review — silently broken unless `getSubscriptions()` is guaranteed to return the exact same object instances every call, which is not part of its contract and not a safe assumption to build on.
- *A persisted "check in progress" flag on `Subscription` (001)*: rejected — this is purely an in-process, single-tab concern (Obsidian runs one plugin instance per vault window); persisting it would add a field to 001's shape and a durability concern (a crash mid-check leaving a stale "in progress" flag) for no benefit over a plain in-memory set that is naturally empty again on every fresh load.
- *Debounce the recurring tick so it can never fire while a catch-up pass is running*: rejected — more complex than a per-subscription guard, and unnecessarily blocks *other*, unrelated subscriptions' ticks just because one subscription's catch-up is slow.

## 15. Sharing persisted storage with 001's `PluginSettings`

**Decision**: The plugin's single `loadData()`/`saveData()` blob has the shape `{ settings: PluginSettings; subscriptions: Subscription[] }`. `subscriptionStore.ts`'s injected `load`/`save` dependencies (`data-model.md` § Subscription store) are not raw `loadData()`/`saveData()` calls themselves — they are thin adapters (wired in `src/main.ts`, T020) that perform a **read-modify-write** against the whole object: `load` reads the whole object and returns just `.subscriptions`; `save` reads the current whole object, replaces only its `.subscriptions` key with the new array, and writes the whole object back.

**Rationale**: 001 already defines `PluginSettings` as a top-level concept with its own defaults, and Obsidian's plugin data model is a single JSON blob per plugin (there is exactly one `loadData()`/`saveData()` pair, not one per feature). If `subscriptionStore.ts`'s `save` instead called `saveData()` with only `{ subscriptions }`, it would silently erase whatever `settings` a person had already configured (and vice versa if a future settings-save path did the same with `subscriptions`). A read-modify-write adapter is the standard fix for "multiple independent writers sharing one persisted blob" and keeps `subscriptionStore.ts` itself agnostic of `PluginSettings`'s existence — it only ever sees its own `Subscription[]` slice.

**Alternatives considered**:
- *Two separate `saveData()`-backed files/keys*: not possible — Obsidian's plugin data API is a single `loadData()`/`saveData()` pair per plugin; there is no built-in multi-file persistence primitive to reach for instead.
- *`subscriptionStore.ts` imports and reads/writes `PluginSettings` directly*: rejected — couples a feature that has nothing to do with settings to 001's settings shape, when a narrow read-modify-write adapter (owned by whoever wires `main.ts`) achieves the same safety without that coupling.

## 16. Surfacing user-facing notices with Obsidian's `Notice` API

**Decision**: Every user-facing notice this feature raises (FR-012's provider-failure notice, FR-014's truncated-window notice) is shown via Obsidian's built-in `Notice` class (`new Notice(message)`), the standard transient toast mechanism every Obsidian plugin has available — not a custom modal, a status-bar item, or a `console` log. `scheduler.ts` itself never imports or calls `Notice` — it only calls `deps.onFailure?.(subscription, reason)` (contracts/collection-pipeline.md § scheduler.ts), a plain, `obsidian`-independent callback. The **`main.ts` wiring (T020) constructs the actual `onFailure` implementation** that calls `new Notice(...)` with bilingual-ready copy (constitution Principle V). This split is deliberate, not just a style preference: `quickstart.md`'s scenarios exercise `startScheduler` with a stubbed `onFailure` (e.g. `onFailure: () => { notified = true }`) run via plain `node`, outside any real Obsidian host — if `scheduler.ts` also unconditionally constructed a real `Notice` internally, that would attempt to use an Obsidian-runtime-only API in a plain Node script and fail. Keeping `scheduler.ts` itself free of any `Notice` construction is what keeps it testable exactly the way `quickstart.md` already relies on.

**Rationale**: `Notice` requires no new dependency (it's part of the `obsidian` package already used for `requestUrl`/`registerInterval`), works identically on desktop and mobile, and is exactly what Obsidian users expect for "something happened, here's a transient heads-up" — matching FR-012/FR-014's "MUST be able to inform the user" language without inventing a bespoke notification surface. Deciding this now (rather than deferring, as 005 defers its bulk-refresh progress indicator's exact presentation) is low-risk because there is really only one idiomatic choice here, unlike a progress bar's design space.

**Alternatives considered**:
- *A custom modal*: rejected — far heavier than the message warrants ("this subscription's check failed, will retry"), and modals demand dismissal, interrupting the user for a non-blocking background event.
- *Status bar item*: rejected — status bar space is typically reserved for persistent, glanceable state (matches 008's settings-screen ownership more than a one-off transient failure), not one-off notices.
- *Deferring the exact mechanism to implementation, like 005's progress indicator*: rejected for this specific case — `Notice` is Obsidian's own standard idiom for exactly this kind of message, so there is no real design space left to defer; pinning it now costs nothing and removes an unnecessary implementation-time decision.

## 17. Catch-up runs immediately on load, no artificial startup delay

**Decision**: The catch-up pass (Decision 5) runs as soon as `startScheduler` executes during `onload` — there is no artificial delay (no `setTimeout` before the first catch-up pass begins).

**Rationale**: FR-004/SC-002 require catch-up to happen "when the plugin loads," not "shortly after." An artificial delay would only be motivated by concern over many subscriptions all firing network calls at once right as Obsidian starts (competing with other plugins' own `onload` work) — but this feature already paces its own arXiv calls (Decision 11's inter-page delay, and the per-subscription sequential processing of Decision 6), so a burst of *many different subscriptions'* first requests is bounded by how many subscriptions exist, not by this feature choosing to go slower. Introducing a fixed startup grace period would only delay when a user actually sees their off-period papers show up, for a benefit (avoiding a thundering-herd of plugin-load network calls) that this repo's typical vault scale (a handful to a few dozen subscriptions, per 001/002's design assumptions) doesn't actually need protection against.

**Alternatives considered**:
- *A fixed startup delay (e.g. 2-5 seconds) before the first catch-up pass*: rejected — no concrete problem it solves at this feature's expected scale, and it directly delays the exact user-visible outcome (SC-002) this feature exists to deliver promptly.
- *Staggering catch-up passes across subscriptions with small per-subscription delays*: unnecessary — Decision 6's existing sequential processing already prevents concurrent bursts; there is nothing left to stagger.

## 18. Encoding subscription values safely into an arXiv `search_query`

**Decision**: Before building the `all:"<value>"` / `au:"<value>"` / `cat:<value>` clause (Decision 11), a subscription's `value` has any literal `"` characters stripped (arXiv's query syntax uses `"` to delimit a phrase; an unescaped embedded quote would end the phrase early and corrupt the query), and the fully-assembled `search_query` string (including the `submittedDate` clause) is passed through `encodeURIComponent` before being placed in the request URL's query string.

**Rationale**: FR-001/FR-002 let a user type an arbitrary keyword or author value with no format validation described in the spec — that value can contain spaces, punctuation, or (rarely but plausibly) a literal quote character. Stripping embedded `"` before wrapping the value in arXiv's own quote delimiters prevents a malformed query (which could either error or silently search for something other than what the user intended); `encodeURIComponent` on the whole assembled string is the standard, minimal-risk way to make a search string with spaces/special characters safe inside a URL, matching how `requestUrl` expects a fully-formed URL rather than performing its own query-string encoding.

**Alternatives considered**:
- *Reject/validate subscription values containing quotes at registration time (subscriptionStore, FR-001)*: rejected — adds user-facing validation friction for a problem that's fully solved transparently at query-construction time; no reason to make this the user's problem.
- *URL-encode the raw value only, not the whole assembled query*: rejected — arXiv's own `:`/`+`/bracket syntax in `submittedDate:[...]` and the `AND` keyword also need to survive as literal query syntax, not be individually re-encoded piecemeal; encoding the fully-assembled string once is simpler and less error-prone than tracking which substrings need encoding and which don't.

## 19. Formatting `CollectionWindow` bounds as arXiv's GMT date-range syntax

**Decision**: Converting a `CollectionWindow`'s `from`/`to` (epoch ms, per `data-model.md`) into arXiv's `YYYYMMDDTTTT` format MUST use UTC-based `Date` accessors (`getUTCFullYear()`, `getUTCMonth()`, etc., or equivalently `toISOString()`-derived components) — never the local-timezone accessors (`getFullYear()`, `getMonth()`, etc.).

**Rationale**: arXiv's `submittedDate` range is explicitly documented as GMT. `epoch ms` (what `CollectionWindow` already stores, per `data-model.md`) is timezone-agnostic by definition, but formatting it into arXiv's date-string syntax requires picking an explicit timezone for the *rendered* string — using local-timezone `Date` accessors on a machine not set to UTC would silently shift the requested window by the local UTC offset (e.g., a user in UTC+9 would have their catch-up window's boundaries shifted by 9 hours from what `CollectionWindow.from`/`to` actually mean), which would either miss papers right at the window's edge or re-fetch ones just outside it. This is exactly the kind of quiet, hard-to-notice bug that's cheap to prevent by naming the correct accessor family now, before `arxivClient.ts` is written.

**Alternatives considered**:
- *Rely on the implementer to "remember" to use UTC*: rejected — this is precisely the kind of easy-to-get-wrong, hard-to-notice-in-testing (correct in UTC-based CI, subtly wrong for a developer/user in a non-UTC timezone) bug worth pinning down explicitly in research now rather than leaving as an unstated assumption.

## 20. Registration idempotency on `(type, value)`, and label defaulting

**Decision**: `subscriptionStore.register` treats `(type, value)` as a natural, collision-free identity: before creating a new `Subscription`, it checks `list()` for an existing one with the same `type` and `value`; if found, that existing subscription is returned unchanged and the newly-supplied `label`/`checkIntervalHours` are discarded. `label` itself becomes optional in `register`'s input, defaulting to `value` when omitted.

**Rationale (spec Clarification session 2026-07-06)**: Two problems converge here. First, 001 requires every `Subscription` to have a `label`, but nothing in 002 previously said where that value comes from if a caller (a future, simpler settings UI) only collects `value` — defaulting to `value` costs nothing and matches 001's own note that label and value may be identical in content. Second, and more importantly: the scheduler's in-flight guard (Decision 14) keys on `` `${type}:${value}` `` for correctness, not just convenience — if two distinct `Subscription` objects could legitimately share a `(type, value)` pair (e.g. registered twice by mistake, with different labels or intervals), the guard would conflate them, silently skipping one's check whenever the other's happened to be in flight. Making `(type, value)` a true unique key at the point of registration removes this failure mode at its source rather than requiring the scheduler to work around it.

**Alternatives considered**:
- *Allow duplicate `(type, value)` subscriptions, key the in-flight guard some other way (e.g. a generated id)*: rejected — 001 does not define a stable subscription id, so "some other way" would mean adding one just to disambiguate a case (duplicate subscriptions) that has no legitimate use: two subscriptions with the same type and value would search, discover, and process the exact same set of papers, just twice — pure waste, never a feature.
- *Reject registration outright (throw/return an error) when `(type, value)` already exists*: rejected in favor of the friendlier "return the existing one" — a UI (008) that lets a user "add" a subscription that already exists shouldn't need special error-handling for what is, from the user's perspective, a no-op, not a mistake worth surfacing as an error.
- *Merge the newly-supplied label/interval into the existing subscription on a duplicate registration*: rejected — silently changing an existing subscription's label/interval as a side effect of an "add" action would be surprising; a user who wants to change those uses the existing, explicit `setCheckInterval`/relabel path instead (see Decision 21 on why relabeling itself is out of scope for now).

## 21. Editing a subscription's `type`/`value`/`label` after creation is out of scope

**Decision**: Once a subscription is registered, its `type` and `value` can never be changed — only `enabled` and `checkIntervalHours` can (FR-002). To track a different search term, the user deletes the old subscription and registers a new one. `label` similarly has no dedicated "rename" operation in this feature.

**Rationale**: `type`/`value` together define *what* a subscription searches for; changing them mid-life is conceptually closer to replacing the subscription than editing it (the whole collection history, dedup key, and in-flight guard key in Decisions 14/20 are all keyed off `(type, value)`). Scoping this feature to delete-and-recreate for that case avoids a second, parallel "rename" code path whose main job would be re-deriving all of that keyed state anyway. `enabled`/`checkIntervalHours` are safe to support editing in place because nothing else in this feature's design keys off them.

**Alternatives considered**:
- *Support in-place editing of `value`/`label`*: deferred/rejected for v1 — no story in this spec's scope needs it (008's future settings screen can still offer "delete and re-add" as a two-click flow), and supporting it now would mean deciding what happens to the subscription's `lastCheckedAt`/in-flight state mid-edit for a capability nothing currently requires.

## 22. Narrowing 004's input to exactly what it needs, and closing the summary→persist gap

**Decision**: `summarize`'s parameter is `SummarizationInput = { title: string; abstract: string; citationCount: number; citationsKnown: boolean }` — never the full `Paper` — and `persist` gains a second parameter, `summary?: SummaryResult`, carrying `summarize`'s result straight through.

**Rationale**: Two distinct problems, fixed together because they're adjacent in the same call chain. First, a prior draft of this contract had `persist(paper: Paper)` with no parameter for `summarize`'s output — meaning a generated summary/future-directions text had no way to reach 003 at all once produced, silently discarding 004's work on every single paper. `specs-input/004-paper-summarization/spec.md`'s own Assumptions state the intended design directly: 004's "generated text is handed to 003 **as part of a single persist**" — confirming `persist` must carry both the paper and the summary in one call, not two independent hooks with no shared destination. Second, and independently: passing the *full* `Paper` to `summarize` would hand an external summarization provider (004's chosen LLM/API, per its own FR-006) fields it has no legitimate use for — `sourceId`, `references`, `authors`, `publicationYear` — when 004's actual generation logic only ever needs the abstract (content to summarize), the title (context), and `citationCount`/`citationsKnown` together (to decide summary-only vs. summary-plus-future-directions, per 004 FR-004 and its Edge Cases). Sending less data to a third-party provider than the full internal `Paper` shape is a direct, low-cost application of constitution Principle IV's transparency expectation — the smaller the payload leaving the vault, the smaller the disclosure surface.

**Alternatives considered**:
- *Keep `persist(paper: Paper)` and give `pipeline.ts` a third hook to write the summary separately (e.g. `attachSummary`)*: rejected — reintroduces exactly the "two independent writes to the same paper's pairing" race that 003's own FR-014 (serialized writes per paper) exists to prevent; a single `persist` call carrying everything for one paper is simpler and matches 004's own stated design intent.
- *Pass the full `Paper` to `summarize` for simplicity/future-proofing*: rejected — no current or foreseeable need in 004's spec for the extra fields, and it works against, not with, the project's data-minimization instincts for anything that leaves the vault to a third party.

## 23. `alreadyPersisted`/`persist` depend on a 003 read/query capability — now recorded as 003 FR-015

**Decision**: This feature's contract continues to define `alreadyPersisted(sourceId): Promise<boolean>` and `persist(paper, summary?): Promise<void>` as hooks 002 calls. The read/existence-check capability these depend on — originally flagged here as *absent* from 003's spec (whose FR-001 through FR-014 were exclusively create/update/delete) — has since been added to `specs-input/003-paper-note-persistence/spec.md` as **FR-015** (expose an existence-check by `sourceId` and a read-back of stored records into canonical `Paper` shape), naming 002's dedup, 005's per-paper read, and 006's full read as its consumers. `alreadyPersisted` maps onto FR-015's existence check; `persist`'s upsert onto FR-004/FR-008's update-in-place. This feature still does not invent or stand in for that capability — it is now a named, mutually-referenced dependency rather than an unstated assumption.

**Rationale**: This was never unique to 002 — at least two other features share the identical dependency: 005's bulk refresh mode needs to enumerate "every saved paper whose `publicationYear` is within the last year," and 006 (graph-data conversion) needs to read back every persisted record to build graph nodes/edges. All three consumers were building on an assumption 003's spec did not yet promise anything about (003's own Open Questions OQ-6/OQ-8/OQ-9 — in-memory index vs. on-demand reads, load-time scan cost, per-paper files vs. a single index — remain the unresolved *implementation* questions for how FR-015 is served, but the capability itself is now a stated requirement). Recording this as 003 FR-015 means 003's author designs against a concrete, cross-feature-sourced requirement rather than discovering the need after 002/005/006 are already built against an unstated assumption.

**Alternatives considered**:
- *002 keeps its own in-memory or on-disk index of what it has collected, independent of 003*: rejected — this feature explicitly writes no files (spec.md Key Entities) and 003 is the sole owner of persisted state; a shadow index in 002 would risk drifting from 003's actual store (e.g., if a paper is later deleted through 003 directly) and duplicates state that has exactly one legitimate owner.
- *Silently assume 003 will "figure it out" without recording the dependency*: rejected — this is precisely the kind of cross-feature contract gap that is cheap to name now and expensive to discover later, once 003, 005, and 006 are all independently specified without anyone having written down that they share this one unmet need.

## 24. `runSubscriptionCheck`: the composition point no earlier draft actually built

**Decision** (signature shown here is the original; **amended by Decision 26** — the last two params are now the live getters `isSummarizationEnabled: () => boolean` / `getSemanticScholarApiKey: () => string | undefined` — and **by Decision 32** — the return type is now `Promise<{ truncated: boolean; coveredThrough: number }>`; see `contracts/collection-pipeline.md` for the current shape): `pipeline.ts` exports `runSubscriptionCheck(subscription, window, hooks, summarizationEnabled, semanticScholarApiKey): Promise<{ truncated: boolean }>` — the concrete function supplied as `startScheduler`'s `runCheck` dependency. Its body is exactly: call `queryArxiv(subscription, window)` (Decision 11), map each of its `entries` through `parseArxivEntry` (Decision 2/13/25 — **not** `parseArxivAtom`, which takes a whole XML document rather than one already-parsed entry) into an `AsyncIterable<PaperCandidate>`, hand that to `runCollectionPass`, and return `{ truncated }` exactly as `queryArxiv` reported it.

**Rationale**: A review of every task against the contracts surfaced that nothing actually built this glue — `scheduler.ts` calls whatever `runCheck` it's given (by design, Decision 4's DI-via-callback approach), and every *other* piece (`queryArxiv`, `parseArxivEntry`, `runCollectionPass`) was individually specified, but the function that composes them into the one `runCheck` a real caller needs had silently fallen through the cracks. Naming and contracting it explicitly — rather than leaving it as an implicit detail of `main.ts`'s wiring task — makes it independently testable (a caller can exercise `runSubscriptionCheck` directly with a stubbed `PipelineHooks`, without needing a real `Plugin`/`registerInterval` at all) and gives it a home consistent with `pipeline.ts` already owning "per-paper orchestration" — this is the same kind of orchestration one level up (per-subscription, not per-paper).

**`runCheck`'s return type also changed** from `Promise<void>` to `Promise<{ truncated: boolean }>` as part of this fix: the scheduler contract previously said a truncated-window notice fires "when a catch-up/tick's provider response reports `truncated: true`" without ever specifying *how* the scheduler would learn that a resolved (non-throwing) `runCheck` call had encountered truncation. Returning it directly is the simplest fix — no new shared mutable state, no second callback, just a value the scheduler already has in hand right where it needs it (immediately after `await runCheck(...)` succeeds).

**Alternatives considered**:
- *Leave the composition implicit in `main.ts`'s wiring task*: rejected — exactly how this gap went unnoticed for this long; a substantial piece of orchestration logic (network call → parse → batch pipeline) deserves its own named, contracted, independently-testable function, not an undocumented implementation detail of a Polish-phase task.
- *Signal truncation via `onFailure` alone, keep `runCheck` returning `void`*: rejected — this still leaves unanswered *who* calls `onFailure('truncated')` and from *what* information, since `runCheck`'s caller (the scheduler) has no way to know a resolved call was truncated unless the value comes back through the call itself; a return value is more direct than inventing a side-channel for one boolean.

## 25. Reconciling `queryArxiv`'s already-parsed entries with `parseArxivAtom`'s whole-document input

**Decision**: Split arXiv parsing into two functions. `parseArxivEntry(entry: Element): PaperCandidate` operates on a single already-parsed Atom `<entry>` node — this is what `queryArxiv` (Decision 11/12's pagination logic) actually produces as its `entries` array, since counting entries per page (to know whether a page was "full" and another page is needed) already requires parsing the response with `DOMParser` before `arxivParser.ts` ever sees it. `parseArxivAtom(xml: string): PaperCandidate[]` becomes a thin convenience wrapper — parse the whole document, then map every `<entry>` through `parseArxivEntry` — kept for quickstart/manual-testing convenience where a whole sample Atom document is the natural input, but not used by `runSubscriptionCheck` (Decision 24), which maps `queryArxiv`'s `entries` through `parseArxivEntry` directly.

**Rationale**: An earlier draft of this contract had `queryArxiv` returning `entries: unknown[]` described as "raw Atom `<entry>` DOM nodes" while `parseArxivAtom`'s only exported signature took a whole XML *string* — two functions that were supposed to compose (in `runSubscriptionCheck`) but had incompatible types, since re-serializing already-parsed DOM nodes back into an XML string just to re-parse them would be both nonsensical and wasteful. This was caught by re-checking the actual data flow between `arxivClient.ts` and `arxivParser.ts`'s exported contracts rather than assuming a `runSubscriptionCheck`-shaped function could bridge any two typed outputs. Splitting the per-entry logic out (rather than, say, changing `queryArxiv` to return a raw XML string, or changing `parseArxivAtom` to accept `Element[]`) was chosen specifically because it **preserves T006/T008's independence** — `arxivClient.ts` only ever needs the standard `DOMParser` (already justified in Decision 1/2) to extract and count entries for its own pagination bookkeeping; it never needs to import `arxivParser.ts`, so the two files remain parallelizable, unlike the alternatives below.

**Alternatives considered**:
- *Change `queryArxiv` to return the raw XML string(s) per page instead of parsed entries*: rejected — `queryArxiv` already needs to know how many entries a page contained (via `DOMParser`) to decide whether to fetch another page (Decision 11); throwing that parsed structure away just to hand back a string, which `arxivParser.ts` would then re-parse from scratch, duplicates the DOM-parsing work for no benefit.
- *Change `parseArxivAtom`'s signature to accept `Element[]` instead of `xml: string`*: rejected — this would silently break `quickstart.md`'s existing scenario (which feeds a plain XML string, matching how a developer would naturally hand-write a test fixture) and removes the standalone "whole document in, candidates out" convenience the function's name implies; splitting into two functions serves both use cases without compromising either.
- *Have `arxivClient.ts` import `arxivParser.ts` and return `PaperCandidate[]` directly from `queryArxiv`*: rejected — this makes T006 depend on T008 for no architectural reason (client concerns — HTTP, pagination, rate-limiting — and parsing concerns are cleanly separable), and was exactly the kind of coupling this feature's task breakdown otherwise avoids (e.g., Decision 20's care to keep T008/T009 mutually independent via a shared T003 helper rather than one depending on the other).

## 26. Reading `summarizationEnabled`/API key live, and discarding a stale in-flight summary

**Decision**: `runCollectionPass` and `runSubscriptionCheck` accept `isSummarizationEnabled: () => boolean` and `getSemanticScholarApiKey: () => string | undefined` — **functions**, not plain `boolean`/`string | undefined` values. `runCollectionPass` calls `isSummarizationEnabled()` twice per candidate: once before deciding whether to call `hooks.summarize` at all, and once again immediately after `hooks.summarize` resolves, using the *second* call's result to decide whether to keep or discard that summary (an `undefined` `summary` is passed to `hooks.persist` if the second check comes back `false`, regardless of what `hooks.summarize` actually returned). `getSemanticScholarApiKey()` is called **once per check**, at the moment Phase 1's single batch-enrichment call is issued (Decision 33) — not once per candidate — since batching (FR-027) means there is exactly one enrichment request per check for the key to apply to, not one per paper. `main.ts` (T020) wires these as `() => this.settings.summarizationEnabled` / `() => this.settings.semanticScholarApiKey` — reading through `this.settings` at call time, never captured into a separate local variable first.

**Rationale (spec Clarification session 2026-07-06, FR-021)**: A plain `boolean` parameter, captured once when `main.ts` constructs the `runCheck` closure during `onload`, would freeze whatever the setting was at plugin-load time for the rest of the session — a user turning summarization off later would have no effect on already-scheduled checks. Beyond that staleness problem, `004-paper-summarization`'s own FR-009 requires "discarding any in-flight generation" when the feature is turned off mid-generation — but 004 has no way to know a setting changed after it was already invoked (it received a plain input, generated a result, and returned it; it isn't polling the setting itself). Since **002 is the sole caller that decides whether and when to invoke 004** (004's own Assumptions state this explicitly), 002 is the only place that can re-check "is this still wanted?" after the fact and act on a "no" by discarding the result — so implementing FR-009's in-flight-discard requirement is unavoidably 002's responsibility, not something 004 can satisfy on its own regardless of how 004 itself is implemented. A live getter function is the simplest mechanism that makes both the "read live" and "re-check after resolving" behaviors possible without inventing a cancellation/abort protocol for `summarize` itself.

**Alternatives considered**:
- *Capture `summarizationEnabled: boolean` once, accept staleness*: rejected — directly contradicts 004's own FR-009, which 002's Out of Scope section says it merely *sequences* rather than reimplements, but sequencing still requires 002 to actually honor the timing-sensitive part of that requirement.
- *Give `PipelineHooks.summarize` a cancellation token so 004 can abort itself*: rejected — 004's spec never describes an abort/cancellation capability, and inventing one here would mean speculatively designing part of 004's contract from 002's side; a caller-side re-check after the fact achieves the same observable outcome (stale result never persisted) without requiring 004 to support cancellation at all.
- *Poll the setting on an interval and cancel in-flight checks*: rejected — far more complex than checking a value twice around an existing `await`, for no additional benefit.

## 27. Subscriptions due in the same tick are checked sequentially, not concurrently

**Decision**: When a scheduler tick (or the catch-up pass) finds multiple subscriptions due at once, `startScheduler` awaits each subscription's `runCheck` to settle before starting the next one's — a plain `for...of` loop with `await` inside, never `Promise.all`/`Promise.allSettled` over the due subscriptions.

**Rationale (spec Clarification session 2026-07-06, FR-022)**: Nothing in the spec previously said whether multiple due subscriptions run concurrently or one at a time — an omission worth closing given this feature's consistent theme of "sequential, not concurrent" processing everywhere else it applies (FR-013's batch processing, Decision 6). Running N subscriptions' checks concurrently would multiply simultaneous outbound requests to arXiv/Semantic Scholar by N at the exact moment they're all due (e.g., right after a long off period, when many subscriptions' catch-up passes could become "due" together) — working directly against the rate-limit conservatism already built into `queryArxiv`/`fetchSemanticScholarPaper` (Decisions 11, 12). Sequential-across-subscriptions is also simpler to reason about alongside the in-flight guard (Decision 14): at most one `runCheck` is ever running at a time, so there is no scenario where two *different* subscriptions' guard entries are being added/removed concurrently on the same tick.

**Alternatives considered**:
- *Concurrent (`Promise.all`) checks across due subscriptions*: rejected — directly undermines the rate-limit conservatism already designed into the provider clients, for a promptness benefit this feature's scale (a user's personal subscription list, not a multi-tenant service) doesn't need.
- *Bounded concurrency (e.g., 2-3 at a time)*: rejected as unnecessary complexity — no evidence a fully sequential approach is too slow for realistic subscription counts, and it avoids having to pick and justify a concurrency limit.

## 28. Skipping a single structurally-incomplete arXiv entry without failing the batch

**Decision**: `parseArxivEntry(entry: Element): PaperCandidate | undefined` returns `undefined` (not a thrown exception) when the entry lacks what's needed to construct a `PaperCandidate` at all (most importantly, no extractable `<id>` to build a `sourceId` from). `parseArxivAtom` and `runSubscriptionCheck` both filter out `undefined` results before continuing — a single bad entry never aborts parsing the rest of a page or the rest of a check.

**Rationale (spec Clarification session 2026-07-06, FR-023)**: This is a distinct failure mode from FR-011's "missing publication year" hold-back (which `promote`/`toPaper` already handles for a *structurally valid* candidate) — here the entry can't even become a candidate in the first place. Returning `undefined` rather than throwing mirrors the exact pattern `toPaper` already established for the year case (Decision in 001) and matches 006's own "one malformed record must not fail the whole conversion" rule (FR-006 there) — applying the same "skip, don't abort" philosophy at the parsing layer that 006 applies at the persisted-record-reading layer, for consistency across the plugin.

**Alternatives considered**:
- *Throw and let the caller catch per-entry*: rejected — forces every caller of `parseArxivEntry` to wrap each call in its own try/catch, whereas a `T | undefined` return composes directly with the same "skip falsy results" filtering the caller already needs for other reasons (matching `toPaper`'s existing convention rather than introducing a second one).
- *Fail the whole `queryArxiv` call if any entry is malformed*: rejected — one bad entry in an otherwise-good page of 100 would needlessly discard 99 good ones, directly contradicting FR-013's "don't let a large/imperfect batch break collection" spirit.

## 29. Clamping a search window when the system clock moves backward

**Decision**: `computeCollectionWindow(subscription, now)` computes `from` as today, then clamps: `const from = Math.min(subscription.lastCheckedAt ?? (now - 24 * 3_600_000), now); const to = now;` — if `from` would otherwise exceed `to` (i.e., `lastCheckedAt` is in the future relative to `now`), the window collapses to `{ from: now, to: now }` (an empty, zero-width window) rather than being sent to a provider with `from > to`.

**Rationale (spec Clarification session 2026-07-06, FR-024)**: A system clock can move backward (manual adjustment, NTP correction, suspend/resume drift) — while rare, `lastCheckedAt` is a plain epoch-ms number with no protection against this. arXiv's `submittedDate:[from TO to]` syntax has no documented, specified behavior for an inverted range; sending one is more likely to produce an error or an ambiguous empty/full response than a well-defined one. An empty window is the closest honest answer to "we don't know what's new since a time that, according to the clock right now, hasn't happened yet" — and still advances `lastCheckedAt` to `now` so the subscription doesn't get stuck re-attempting the same nonsensical window every tick.

**Alternatives considered**:
- *Pass the inverted range through to the provider as-is*: rejected — relies on undocumented provider behavior for an edge case worth handling deterministically ourselves instead.
- *Skip the check entirely and don't advance `lastCheckedAt`*: rejected — this would cause the subscription to attempt the same (still nonsensical, until the clock corrects itself) computation on every subsequent tick, potentially indefinitely, rather than a one-time no-op pass.

## 30. Rejecting registration of an empty or whitespace-only subscription value

**Decision**: `subscriptionStore.register` rejects (its returned `Promise` throws/rejects) when `input.value.trim().length === 0`, before checking for an existing `(type, value)` match or persisting anything.

**Rationale (spec Clarification session 2026-07-06, FR-025)**: Unlike an out-of-range check interval (FR-005's rejection rule, which has a well-defined fallback: keep the prior valid value), a brand-new registration with an empty value has no prior value to fall back to and no sensible "search for nothing" behavior — creating such a subscription would either search inappropriately broadly (arXiv's `all:""` is not a meaningful empty-string query) or simply never find anything, either way misleading the user into thinking a subscription is tracking something. Rejecting outright, the same way a completely invalid subscription `type` would be rejected, is the more honest response to what is unambiguously a data-entry mistake rather than a legitimate degenerate case.

**Alternatives considered**:
- *Silently register it, let it just never match anything*: rejected — leaves a "dead" subscription in the user's list with no indication anything is wrong, which is worse than an immediate, explicit failure at registration time.
- *Trim and store the trimmed value even if the original had surrounding whitespace, but only reject if empty after trimming*: this is exactly what's decided — trimming happens as part of the emptiness check, not as a separate normalization decision needing its own justification.

## 32. arXiv result ordering, and advancing `lastCheckedAt` only over the covered portion of a truncated window

**Decision (spec Clarification session 2026-07-06 (continued), FR-026)**: `buildArxivSearchUrl` (Decision 11) MUST pin arXiv's result ordering explicitly by appending `&sortBy=submittedDate&sortOrder=ascending` to every query — never relying on arXiv's default `relevance` sort. `queryArxiv` MUST return, alongside `entries`/`truncated`, a `coveredThrough: number` (epoch ms): when the window was fully covered (`truncated === false`), `coveredThrough === window.to`; when the query truncated at the `ARXIV_MAX_PAGES` cap (`truncated === true`), `coveredThrough` is the `<published>` (submission) timestamp of the **last (newest, since ascending) entry actually fetched with a parseable `<published>`**. `runSubscriptionCheck` threads this value up unchanged, and `scheduler.ts` records `lastCheckedAt` via `onSubscriptionChecked(subscription, coveredThrough)` — **not** `window.to` — so a truncated window advances `lastCheckedAt` only to the boundary genuinely covered.

**Fallback when the boundary entry's `<published>` is missing or unparseable** (closes a gap found in analysis review): the newest-fetched entry can itself be one of the structurally-incomplete entries FR-023/Decision 28 already anticipates. Since `coveredThrough` feeds directly into the persisted `lastCheckedAt`, it MUST NEVER be `NaN`/`undefined`/thrown from a parse failure — that would corrupt or crash a subscription's future checks, exactly the class of failure this decision exists to prevent. `queryArxiv` MUST therefore compute `coveredThrough` by scanning fetched entries from newest to oldest and using the first one with a parseable `<published>`; if none of the fetched entries in a truncated page has a parseable `<published>` at all, `coveredThrough` MUST fall back to `window.from` (no progress that pass, but never an invalid or corrupting value) rather than propagate an error or an unparseable timestamp.

**Rationale**: Without a pinned sort, arXiv orders by *relevance*, so a window that overflows the 1,000-entry cap (Decision 11) returns an arbitrary, non-contiguous relevance-ranked subset scattered across the whole date range. The prior contract advanced `lastCheckedAt` to `now` on truncation regardless — which, combined with relevance ordering, **permanently loses every paper in that window beyond the cap** (the next check starts from `now`, never revisiting them), and FR-014's "notify the user" only reports the loss, it does not recover it. Sorting by `submittedDate` ascending makes the fetched portion a contiguous prefix of the window `[from, lastFetchedSubmittedDate]`; advancing `lastCheckedAt` only to `lastFetchedSubmittedDate` means the uncovered tail `(lastFetchedSubmittedDate, now]` is picked up on the very next tick, so a pathological window is covered across successive checks instead of being silently truncated-and-lost. Progress is guaranteed: each pass advances the boundary by up to 1,000 papers, so even a huge backlog drains monotonically rather than re-fetching the same oldest 1,000 forever. `<published>` (arXiv Atom's original-submission datetime, aligned with the `submittedDate` sort key) is the correct boundary field; ties at the exact boundary minute are harmless because the next window re-includes that instant and `dedupe.ts`/`alreadyPersisted` (Decision 8) collapse the re-fetch.

**Alternatives considered**:
- *Keep advancing to `now` on truncation, accept the loss, rely on FR-014's notice*: rejected — a user-facing "couldn't cover the whole window" toast is not a substitute for actually collecting the papers; silent permanent data loss is exactly the failure `sourceId`-stable, window-advancing collection is meant to avoid.
- *Don't advance `lastCheckedAt` at all on truncation*: rejected — the next check would re-query `[from, now]`, re-fetch the same oldest 1,000, truncate again, and never make progress (an infinite non-advancing loop).
- *Sort descending (newest first) and advance to the oldest fetched*: rejected — symmetric in theory, but ascending + "advance to newest fetched" keeps the already-collected region a single contiguous `[from, boundary]` prefix that matches how `lastCheckedAt` is defined (everything up to it is done), which is easier to reason about than a `[boundary, to]` suffix with a still-uncovered `[from, boundary)` head.
- *Let a missing/unparseable `<published>` on the boundary entry propagate as `NaN`/an exception*: rejected — `coveredThrough` is written straight into a persisted field; an invalid value there is worse than the truncation problem this decision fixes, since it can corrupt a subscription's `lastCheckedAt` permanently instead of merely delaying full coverage by one pass.

## 33. Enriching a batch of papers through Semantic Scholar's batch endpoint, not one request per paper

**Decision (spec Clarification session 2026-07-06 (continued), FR-027)**: Citation enrichment for a check's promotable candidates MUST use Semantic Scholar's batch endpoint — `POST /graph/v1/paper/batch?fields=citationCount,references.paperId,references.externalIds` with a JSON body `{ "ids": ["ARXIV:<id>", ...] }` (up to 500 ids per call, chunked when more) — rather than one `GET /graph/v1/paper/ARXIV:<id>` per paper. `enrichFromSemanticScholar` changes from a single-candidate call to a batch call: `enrichFromSemanticScholar(candidates: PaperCandidate[], apiKey): Promise<Map<PaperSourceId, EnrichmentOutcome>>`. `runCollectionPass` therefore first drains its candidate iterable, applies the dedupe/`alreadyPersisted`/promotable filters (Decisions 8, and FR-011's year gate), batch-enriches the surviving set (chunked ≤500), then runs the existing sequential per-paper summarize→persist loop (Decision 6) using the pre-fetched outcome map — no per-paper enrichment network call inside that loop. Per the batch response, a paper returned as `null` (Semantic Scholar has no record for that arXiv ID) maps to `EnrichmentOutcome.status: 'terminalAbsence'`; a whole-request `429`/network failure retries the chunk a bounded 3 times (Decision 7's spacing) before mapping every id in that chunk to `'transientFailure'`.

**Rationale**: Semantic Scholar's **unauthenticated** rate pool is a single, undocumented limit shared across every anonymous caller worldwide (spec Clarification 2026-07-06 / FR-020) — on the order of ~1 request/second in practice. A catch-up pass or a freshly-registered broad subscription can surface dozens to hundreds of new papers at once; issuing one `GET` per paper (the prior Decision 12 shape) would systematically hit `429`, and each `429` then burns this feature's bounded per-paper retries (Decision 7), cascading a single busy check into minutes of backoff. The batch endpoint collapses N papers into `ceil(N/500)` requests — for essentially every realistic check, exactly **one** request — which is both dramatically kinder to the shared pool and far less likely to be throttled, while an optional API key (FR-020) still further raises the ceiling. The cost is that candidates are materialized into an array before the sequential loop rather than being enriched in a pure stream; this is acceptable because Decision 11's 1,000-entry cap already bounds a single check's candidate set, and FR-013's "no UI freeze" guarantee is preserved for the genuinely expensive per-paper work (summarization + persistence), which remains one-at-a-time with event-loop yields (Decision 6).

**Amends Decision 12**: the single-paper `GET /paper/ARXIV:<id>` lookup and `fetchSemanticScholarPaper` are replaced by the batch `POST /paper/batch` and `fetchSemanticScholarBatch`; the 404→terminalAbsence mapping becomes "a `null` array element → terminalAbsence for that id"; the `x-api-key` header handling (FR-020) is unchanged (added when the key is present, omitted otherwise). The single-paper lookup remains the shape **005**'s per-paper manual refresh naturally uses (one paper at a time), so `fetchSemanticScholarPaper` is not deleted from the provider client — 002's *collection* path just no longer calls it.

**Closing a gap found in analysis review — applying an `'enriched'` outcome to its candidate before promotion**: `enrichFromSemanticScholar` (this decision) only *returns* a `Map<PaperSourceId, EnrichmentOutcome>` — it never mutates or returns an updated `PaperCandidate`. But 001's `toPaper` (`promotion.ts`'s `promote`, delegating directly to it) derives `citationsKnown` as `candidate.citationCount !== undefined` — it looks at the *candidate's own* `citationCount`/`references` fields, not at any separate enrichment result. This means Phase 2 of `runCollectionPass` MUST, for each surviving candidate, look up its outcome in the map and — when `status === 'enriched'` — **apply `outcome.citationCount`/`outcome.references` onto the candidate itself** (`{ ...candidate, citationCount: outcome.citationCount, references: outcome.references }`) *before* calling `promote`; for `'terminalAbsence'`/`'transientFailure'`, the candidate is passed to `promote` unchanged (its `citationCount`/`references` stay `undefined`, so `toPaper` derives `citationsKnown = false` exactly as intended). Without this explicit apply-then-promote step, a successfully-enriched candidate would still promote with `citationsKnown = false` — silently defeating enrichment for every paper it succeeds on, which is precisely the FR-018/SC-007 guarantee this feature exists to provide.

**Alternatives considered**:
- *Keep one GET per paper, add a fixed inter-call delay*: rejected as the primary fix — pacing N sequential calls still costs N requests and, at ~1 rps unauthenticated, makes a 200-paper catch-up take minutes even without any `429`; the batch endpoint solves the root cause (request count) rather than merely spacing the symptom.
- *Batch, but also keep enrichment inside the streaming per-candidate loop via a coalescing buffer*: rejected — a look-ahead buffer that groups streamed candidates into batches of 500 adds real complexity (windowing, flush-on-end) for no benefit over simply materializing the already-capped (≤1,000) candidate set and chunking it.

## 34. Checking a newly-registered subscription immediately, not only on the next 15-minute tick

**Decision (spec Clarification session 2026-07-06 (continued), FR-028)**: A subscription that is *genuinely newly created* by `subscriptionStore.register` (not an idempotent hit on an existing `(type, value)`, Decision 20) MUST have its first check begin right away, without waiting up to 15 minutes for the next scheduler tick. Implemented without coupling the store to the scheduler: `SubscriptionStoreDeps` gains an optional `onRegistered?: (subscription: Subscription) => void` fired only after a genuinely-new registration has been persisted; `startScheduler` returns a handle `{ checkNow(subscription: Subscription): Promise<void> }` that runs the exact same due-check code path a tick uses (same `computeCollectionWindow`, same in-flight guard by `type:value`, same `runCheck`/`onSubscriptionChecked`/`onFailure` wiring — Decisions 5/14). `main.ts` (T020) wires `onRegistered` to `scheduler.checkNow`, so registration → immediate check, while the store itself stays unaware the scheduler exists.

**Rationale**: A brand-new subscription has `lastCheckedAt === null`, so the recurring tick (Decision 4) already treats it as due — the only defect is latency: the user adds "graph neural networks" and sees nothing for up to ~15 minutes, which reads as "the plugin isn't working." Triggering an immediate check on registration closes that gap while reusing the tick's own machinery (so there is no second, divergent check implementation, and the in-flight guard still prevents the immediate check and the next tick from double-processing the same subscription). Routing the trigger through an `onRegistered` callback + a `checkNow` handle (rather than having `register` call the scheduler directly) keeps `subscriptionStore.ts` free of any dependency on `scheduler.ts` — the two are still composed only in `main.ts`, matching this feature's existing dependency-injection seams (Decision 10). Firing only on a genuinely-new registration (not an idempotent re-register) avoids a redundant immediate check when the user re-adds something already tracked.

**Alternatives considered**:
- *Do nothing; accept up to ~15 min latency*: rejected — a visible, avoidable "did my subscription register?" gap for the single most common first interaction with the feature.
- *Have `register` import and call the scheduler directly*: rejected — couples the store to the scheduler for a wiring concern `main.ts` already owns; the callback seam keeps the store independently testable.
- *Shorten the tick to make the wait smaller*: rejected — punishes battery/mobile for every subscription forever to paper over one first-check latency; a targeted immediate check is strictly better.

## 35. Re-enabling a long-disabled subscription keeps off-period (catch-up) semantics

**Decision (spec Clarification session 2026-07-06 (continued), FR-029)**: When a subscription is re-enabled after a period disabled, its next check uses the ordinary `computeCollectionWindow` — `[lastCheckedAt, now]` — exactly as a plugin-was-off catch-up does; re-enabling does **not** reset `lastCheckedAt` to `now` or clamp the look-back to 24h. Because `lastCheckedAt` did not advance while disabled (no checks ran, FR-010), the window naturally spans the whole disabled span, and Decision 32's truncation-aware advancement covers that span across successive checks if it exceeds one query's cap.

**Rationale**: A disabled subscription is, from the user's tracking perspective, indistinguishable from the whole plugin being off for that subscription — the user still wants the papers that appeared meanwhile once they turn it back on, which is precisely User Story 3's catch-up promise (FR-004). Treating re-enable like registration (window reset to now/24h) would silently drop everything published during the disabled period, re-introducing exactly the "off = permanent blind spot" the catch-up design exists to prevent. Keeping one window rule (`computeCollectionWindow`) for load-catch-up, regular ticks, immediate-on-register (Decision 34 uses it too), and re-enable means there is a single behavior to reason about, and Decision 32 already guarantees an arbitrarily large resulting window is covered without loss rather than truncated-and-dropped.

**Alternatives considered**:
- *Reset the window to `[now - 24h, now]` (or `[now, now]`) on re-enable*: rejected — drops the disabled-period papers, contradicting the catch-up guarantee; a user who disabled a noisy subscription for a week and re-enabled it almost certainly still wants that week's results, not a silent gap.
- *Prompt the user to choose "catch up" vs "from now" on re-enable*: rejected as premature UX complexity — the catch-up default is the safe, consistent choice; a "start fresh" option, if ever wanted, is a future additive setting, not a decision to force at every re-enable.

## 36. Making enrichment injectable so `quickstart.md` can test it without a live network call

**Decision (gap found in analysis review — `runCollectionPass`/`runSubscriptionCheck` amended)**: Both functions gain an optional final parameter, `enrich?: (candidates: PaperCandidate[], apiKey: string | undefined) => Promise<Map<PaperSourceId, EnrichmentOutcome>>`, defaulting to the real `enrichFromSemanticScholar` (contracts § enrichment.ts) when omitted. `runSubscriptionCheck` forwards its own `enrich` parameter to `runCollectionPass` unmodified. `main.ts` (T020) never passes this parameter — production code always gets the real, network-calling implementation via the default.

**Rationale**: Decision 10 already established dependency injection for `summarize`/`persist`/`alreadyPersisted` specifically so `pipeline.ts` could be implemented and *tested* without 003/004 existing yet, and specifically so `quickstart.md` never makes a live call. Enrichment was the one exception: `enrichFromSemanticScholar` was called directly inside `runCollectionPass`, with no seam for a caller to substitute a stub. This directly contradicted `quickstart.md`'s own stated premise ("stubs both provider clients so no requestUrl call ever fires") — every quickstart scenario that exercises `runCollectionPass` with a real, non-empty candidate would, as actually specified, trigger a genuine Semantic Scholar network request, since there was no way to intercept it short of monkey-patching the `enrichment.ts` module. An optional parameter with a default matches this feature's existing DI pattern exactly (same shape of fix as Decision 10), costs production callers nothing (they simply never pass it), and closes the gap between quickstart's stated guarantee and what the contract actually allowed to be tested.

**Alternatives considered**:
- *Fold `enrich` into `PipelineHooks` as a required field*: rejected — `PipelineHooks` specifically represents the seam to 003/004 (features that don't exist yet); enrichment is this feature's own, already-implemented logic, so forcing every caller (including `main.ts`) to explicitly wire a real `enrichFromSemanticScholar` reference for a capability that's always available by default adds boilerplate with no benefit over a default parameter.
- *Leave `enrichFromSemanticScholar` un-injectable and instead have `quickstart.md` monkey-patch/mock the module or the underlying `requestUrl` call*: rejected — module-level mocking is fragile (depends on how the bundler/`import` resolves at runtime), harder to read than passing a plain function argument, and inconsistent with how every other external dependency in this feature (summarize, persist, alreadyPersisted, even `now` in `SchedulerDeps`) is already made testable via a plain injected parameter.
- *Do nothing; accept that quickstart's "no live network call" claim doesn't fully hold for enrichment-exercising scenarios*: rejected — this repo has no automated test runner (per `CLAUDE.md`), so `quickstart.md` is the *only* verification mechanism this feature has; a verification script that can silently hit a real third-party API contradicts its own stated purpose and this repo's "no network calls without an obvious, disclosed reason" posture (constitution Principle IV) even during development/testing.
