# Feature Specification: Subscription-Based Paper Collection

**Feature Branch**: `002-subscription-paper-collection`

**Created**: 2026-07-05

**Status**: Draft

**Input**: User description: "Based on the subscriptions a user has registered, periodically find new papers from external academic databases (arXiv, Semantic Scholar). A user registers subscriptions for keywords, authors, or arXiv categories; new papers are collected automatically. All communication with external databases happens only within this feature. Collection does not run while the plugin is off — instead, when the plugin turns back on, it searches for the papers that appeared during the time it was off (the gap between when it stopped and when it started again). Provider responses arrive in provider-specific formats (arXiv as Atom XML, Semantic Scholar as JSON) and are parsed into the canonical paper shape."

## Clarifications

### Session 2026-07-05

- Q: What is the first-collection window for a brand-new subscription (`lastCheckedAt` = null)? → A: Bounded to the shortest allowed check interval (24 hours) looking back from registration, so registering a subscription cannot flood the vault with historical papers.
- Q: Which provider performs discovery (keyword/author/category search)? → A: arXiv performs all discovery; Semantic Scholar is used only to enrich papers already found via arXiv with citation data, never as an independent discovery source.
- Q: What is the scheduling mechanism for per-subscription checks? → A: Each subscription runs its own independent timer keyed to its own check interval, rather than all subscriptions being polled on one shared sweep cadence. **Refined by the 2026-07-06 "every 15 minutes" answer below**: "independent timer" means each subscription tracks its own next-due time (from its own `checkIntervalHours`/`lastCheckedAt`), not a literal separate OS/JS timer object per subscription — the implementation achieves this independence with one shared, coarse recurring check (research.md Decision 4), which is what the 07-06 answer pins to a concrete cadence.
- Q: How is an arXiv paper matched to its Semantic Scholar record for enrichment? → A: Match by arXiv ID first (Semantic Scholar's API accepts arXiv IDs directly); if that yields no match, fall back to a title + first-author match; an unresolved match is treated as an enrichment failure (`citationsKnown = false`), not an error. **Superseded by the 2026-07-06 session below**, which removes the title/author fallback entirely to eliminate false-positive matches.
- Q: What `sourceId` scheme do references/citations supplied by Semantic Scholar enrichment carry? → A: Normalize to the `arxiv:` scheme (001) whenever the referenced work has a known arXiv ID, so graph edges (006) can connect to independently-collected papers; keep a `semanticScholar:`-scheme identifier only when no arXiv ID is available.

### Session 2026-07-06

- Q: The arXiv-ID-first / title+author-fallback matching risks a false-positive match (a common surname's unrelated paper ranking top in a title search), silently attaching the wrong citation data. Should the fallback be kept? → A: No — the title+author fallback is removed entirely. Enrichment matches **by arXiv ID only**. When Semantic Scholar has no record for that arXiv ID, this is treated identically to the existing terminal-absence case (FR-018): `citationsKnown` stays `false`, the paper is promoted and persisted immediately, and only a later manual refresh (005) — or a possible future auto-heal sweep, currently just a deferred idea in `specs-futureworks/010-automatic-citation-refresh`, not a feature that exists yet — may retry. This trades a slightly higher terminal-absence rate (a real but not-yet-Semantic-Scholar-indexed arXiv paper) for zero risk of attaching a wrong paper's citation data.
- Q: arXiv IDs carry a version suffix (e.g. `2301.12345v2`) that changes when an author revises a preprint. Should a paper's `sourceId` include the version? → A: No — `sourceId` MUST be built from the version-stripped base identifier (`arxiv:2301.12345`, never `arxiv:2301.12345v2`), so the same underlying paper always maps to the same `sourceId` regardless of how many times it is revised. A later revision of an already-collected paper is therefore treated as already-persisted (FR-009's dedup) and is not re-collected or updated — refreshing an already-stored paper's content to match a newer arXiv revision is out of scope for this feature.
- Q: If a catch-up pass and the regular scheduled tick both become due for the same subscription at roughly the same time (e.g. a slow catch-up pass still running when the next tick fires), could the subscription be checked twice concurrently? → A: No — the scheduler MUST track which subscriptions currently have a check in flight and skip a subscription that is already being checked, for either the catch-up pass or a regular tick. A skipped subscription is simply picked up on its next due tick, since its `lastCheckedAt` has not yet advanced.
- Q: This feature's `Subscription[]` list and 001's `PluginSettings` both need to be read/written through the plugin's single `loadData()`/`saveData()` call — how is one avoided clobbering the other? → A: The persisted shape is a single object with sibling keys (e.g. `{ settings: PluginSettings, subscriptions: Subscription[] }`); any write MUST read the current whole object, replace only its own key, and write the whole object back (read-modify-write), never overwrite the object wholesale from a partial in-memory copy.
- Q: Semantic Scholar's unauthenticated tier shares a rate limit across every unauthenticated caller worldwide, with no stable, documented number this feature can rely on. Should a user be able to supply their own Semantic Scholar API key for a dedicated, documented rate limit? → A: Yes — this MUST be available as an always-on option, not something added only if unauthenticated access later proves insufficient. A user MAY optionally provide a Semantic Scholar API key in plugin settings (an FR-016-style additive extension to 001's `PluginSettings`); when present, this feature includes it in every Semantic Scholar request. The feature MUST work fully without a key (a key is optional, never required) — its absence only means enrichment shares the unauthenticated pool as already designed.
- Q: 001 requires a subscription's `label` field, but where does its value come from — must the user always type one? → A: `label` is optional at registration; when omitted, it defaults to the subscription's own `value` (001 already permits label and value to be identical in content). This keeps the door open for a future settings UI (008) to offer a dedicated label input without forcing one on a simpler UI that only asks for `value`.
- Q: What happens if a user registers a subscription whose type and value already match an existing one? → A: Registration is idempotent on `(type, value)`: if a subscription with that exact type and value already exists, the existing subscription is returned unchanged rather than creating a duplicate; the newly-supplied label/interval (if any) are ignored in that case — to change an existing subscription's label or interval, use the existing per-subscription update operations (FR-002), not re-registration. This also prevents two "identical" subscriptions from ever colliding under the scheduler's in-flight guard (Clarification above), since `(type, value)` can never appear twice.
- Q: How often does the scheduler actually check "is any subscription due," given check intervals are only defined in whole hours (6/12/24/48/72)? → A: Every 15 minutes. This bounds how late a due check can fire (at most ~15 minutes after its exact due time) to a small fraction of even the shortest allowed interval (6 hours), without waking the plugin unnecessarily often.
- Q: Does the "off-period window could not be fully covered" notice (FR-014) apply only to the catch-up pass, or to any query this feature makes? → A: Any query — a regular scheduled tick's search can in principle also be truncated (e.g., an unusually broad category subscription with a high daily submission volume), and there is no reason to notify the user only when it happens during catch-up. The notice mechanism is shared: both the catch-up pass and a regular tick invoke the same underlying check, so no separate implementation is needed for either call site.
- Q: If a subscription is disabled while its check is already in flight, is the in-flight check aborted, and does its outcome (including `lastCheckedAt`) still apply? → A: The in-flight check is left to finish naturally — it is not aborted, since FR-010 only stops *new* collection, not an already-started one. If it completes successfully, `lastCheckedAt` is still advanced as normal (the window was genuinely searched); the subscription's `enabled = false` simply means no further checks are scheduled afterward.
- Q: If a subscription is *deleted* (not just disabled) while its check is already in flight, what happens to the papers it finds and to the now-nonexistent subscription's `lastCheckedAt`? → A: The in-flight check is likewise left to finish naturally, and any papers it discovers are enriched, optionally summarized, and persisted exactly as if nothing had changed — a paper's validity doesn't depend on the subscription that found it still existing, and the same paper could equally have surfaced via another subscription. The only thing that changes is the bookkeeping step at the very end: `recordChecked` (contracts § subscriptionStore.ts) is a no-op when its target subscription is no longer in the store — it MUST NOT re-insert the deleted subscription to hold a `lastCheckedAt` value nobody will ever read again.

### Session 2026-07-06 (continued)

- Q: If a user turns summarization off (or changes the Semantic Scholar API key) while the scheduler is already running, does the in-flight check pick up the new value immediately, or only after the plugin next loads? Separately, if summarization is turned off while a specific paper's summary generation is already in flight, is that in-flight result discarded? → A: Both MUST reflect the current setting live, not a value captured once at plugin load — every check reads the current `summarizationEnabled`/API key at the moment it runs, not a snapshot from `onload`. For a summary generation already in flight when the setting is turned off mid-generation, this feature MUST re-check the current value after generation completes and discard the result (falling back to the abstract, per 004's own "abstract fallback" behavior) if it is now off, exactly matching 004's own FR-009 ("discarding any in-flight generation") — since 004 has no way to abort or know about a setting change once invoked, this feature (which owns *when* 004 is called) is the only place that can honor FR-009's in-flight-discard requirement, not 004 itself.
- Q: When more than one subscription becomes due in the same scheduler tick (or catch-up pass), are they checked concurrently or one at a time? → A: One at a time, sequentially — matching this feature's existing "sequential, non-freezing" approach to processing within a single subscription's discovered batch (FR-013). Checking multiple subscriptions concurrently would multiply the number of simultaneous outbound requests to arXiv/Semantic Scholar for no benefit this feature's scale needs, and would complicate reasoning about the in-flight guard and rate-limit pacing already established per subscription.
- Q: If a single arXiv Atom entry is structurally incomplete in a way that prevents building a valid candidate at all (e.g., missing the `<id>` element entirely, so no `sourceId` can be constructed) — not just missing a publication year, which is already the FR-011 hold-back case — what happens? → A: That single entry is skipped and the rest of the batch is still processed; this is not treated as a provider-call failure and does not abort the containing check. This mirrors the graph-conversion feature's (006) own "one malformed record must not fail the whole conversion" rule, applied to parsing instead of persisted-record reading.
- Q: If the system clock moves backward (e.g., a manual clock change, or NTP correction) such that "now" is earlier than a subscription's `lastCheckedAt`, what window is searched? → A: An empty window (`from = to = now`) rather than an inverted range — the check still runs and still advances `lastCheckedAt` to `now`, but discovers nothing for that pass, since a provider query with `from` after `to` has no well-defined meaning and must not be sent as-is. **Superseded by the 2026-07-07 session below**: advancing `lastCheckedAt` backward to the earlier "now" was found to re-open an already-covered span once the clock recovers (searching it twice, violating FR-006); the empty-window behavior is kept but `lastCheckedAt` is now left unchanged rather than moved backward (FR-024).
- Q: Can a subscription be registered with an empty or whitespace-only value? → A: No — registration MUST reject (the operation fails; no subscription is created) when the trimmed value is empty, since there is no reasonable "search for nothing" behavior to fall back to and no prior value to keep (unlike an invalid check interval, which has a prior valid value to retain).
- Q: arXiv orders results by relevance unless told otherwise, and a single check caps how many entries it will page (to avoid multi-minute queries). If a window has more matching papers than that cap, which papers get dropped, and does `lastCheckedAt` still advance to `now` — permanently losing the rest? → A: The query MUST pin an explicit `submittedDate` ascending sort (never rely on relevance ordering), so the fetched portion is a contiguous oldest-first prefix of the window; and when a window truncates at the cap, `lastCheckedAt` MUST advance only to the submission time of the last paper actually fetched — never to `now`. The uncovered newer tail is then picked up on the next check, so a too-large window is covered across successive passes instead of being silently lost. The truncation notice (FR-014) still fires, but it now signals "covered so far, more coming next pass," not "these papers are gone."
- Q: Semantic Scholar's unauthenticated rate limit is a single pool shared globally (~1 request/second in practice). A catch-up pass can surface dozens or hundreds of new papers at once — does enrichment issue one request per paper? → A: No — enrichment MUST use Semantic Scholar's batch endpoint (up to 500 arXiv IDs per request, chunked when more), collapsing N papers into roughly one request instead of N. One request per paper would systematically hit the shared rate limit and cascade into per-paper retries/backoff. A paper the batch reports no record for is treated exactly as the single-paper "no such paper" terminal absence was (`citationsKnown = false`).
- Q: When a user registers a brand-new subscription while the plugin is running, does its first check wait for the next scheduled tick (up to ~15 minutes away)? → A: No — a genuinely new registration (not an idempotent re-register of an existing `(type, value)`) MUST trigger its first check immediately, reusing the same check machinery and in-flight guard a scheduled tick uses (so the immediate check and the next tick can never double-process it). This closes the "I added a subscription but nothing happened" gap.
- Q: When a subscription that was disabled for a long time is re-enabled, does its next check catch up on everything published while it was disabled, or start fresh from now? → A: It catches up — the next check covers `[lastCheckedAt, now]` exactly as a plugin-was-off catch-up does (re-enabling does not reset `lastCheckedAt`). A disabled subscription is, for tracking purposes, the same as the plugin being off for it; dropping the disabled-period papers would re-create the "off = permanent blind spot" the catch-up design exists to prevent. If that span is large, the truncation-aware advancement above covers it across successive checks.

### Session 2026-07-07

- Q: The feature only ever collects forward from a subscription's registration (first window bounded to the last 24 hours, then `[lastCheckedAt, now]` onward), so foundational older papers — e.g. the 2017 origin paper for a `transformer` keyword — can never be collected. Should there be a way to reach into the past? → A: Yes, as an explicit, user-triggered one-off per subscription (never automatic on registration, so registering still cannot flood the vault and the opt-in principle holds). Each run collects a user-specified start date up to the subscription's existing forward floor. It runs on two independent watermarks so it never disturbs forward scheduling: `lastCheckedAt` stays the forward frontier, and a new `coveredFrom` (backward floor) plus a `backfillState.cursor` (progress) drive the backward fill. Backfill reuses the exact forward pipeline (discovery/parse/enrich/promote/persist) and dedup, is resumable across the paging cap and plugin restarts (reusing FR-026's truncation → cursor advance), pauses on disable and resumes from its cursor on re-enable, is a no-op when the requested start is not older than `coveredFrom`, and surfaces failures through the existing notice mechanism without advancing its cursor.
- Q: A subscription only checks on its own interval (6–72h). Is there a way for a user to force an existing subscription to check *now* without waiting for its next tick? → A: Yes — a manual, on-demand "check now" for an existing subscription, reusing the same check path and in-flight guard a scheduled tick uses (so the manual check and the next tick can never double-process it). This is the existing-subscription analogue of FR-028's immediate first check for a *newly registered* subscription.
- Q: When the system clock moves backward past a subscription's `lastCheckedAt`, the prior rule advanced `lastCheckedAt` to the earlier "now" — but that re-opens an already-covered span once the clock recovers, searching it twice (FR-006 forbids this). What should happen? → A: The check runs an empty window (discovers nothing) and leaves `lastCheckedAt` unchanged rather than moving it backward, so forward coverage simply resumes with no overlap once the clock is at or past `lastCheckedAt` again.
- Q: A truncated window advances `lastCheckedAt` only to the newest paper with a readable submission time; if *no* fetched paper has a readable time, the prior rule refused to advance at all — which re-fetches the same unreadable prefix on every future tick forever. Is that acceptable? → A: No — that no-advance case must be bounded: if a truncated window makes no forward progress across successive checks because none of its fetchable papers has a readable submission time, the check surfaces the FR-014 notice and advances past that stalled prefix, trading those structurally-incomplete (already unpromotable, FR-023) entries for scheduler liveness rather than stalling forever.
- Q: Two long-standing decisions — the 24-hour bound on a brand-new subscription's first window, and "arXiv is the sole discovery source; Semantic Scholar is enrichment-only" — lived only in Clarifications, not in any verifiable requirement. Should they be promoted to Functional Requirements? → A: Yes — both are foundational (flood prevention and the core provider-routing architecture) and are now stated as FR-030 and FR-031 so they are testable, not merely recorded.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Register and manage subscriptions (Priority: P1)

As a user tracking research trends, I want to register subscriptions for keywords, authors, or arXiv categories I care about and manage them at any time, so that new papers are collected automatically without me searching myself.

**Why this priority**: Without subscriptions there is nothing to collect. Registration and management is the entry point for the entire collection pipeline.

**Independent Test**: Can be fully tested by registering a subscription of each type, viewing the list, disabling one, deleting another, and confirming each action is reflected — using stubbed provider responses so no live network is required.

**Acceptance Scenarios**:

1. **Given** the subscription list, **When** the user enters a type (keyword / author / arXiv category) and a value, **Then** a new subscription is registered with a default check interval and appears in the list.
2. **Given** a registered subscription, **When** the user disables it, **Then** it no longer triggers any new collection.
3. **Given** a registered subscription, **When** the user deletes it, **Then** it is removed from the list and stops triggering collection.
4. **Given** a subscription, **When** the user sets its check interval, **Then** only the five allowed intervals (6/12/24/48/72 hours) defined in 001 are accepted.
5. **Given** the user registers a subscription without specifying a label, **When** it is created, **Then** its label defaults to its value.
6. **Given** a subscription with a given type and value already exists, **When** the user registers that same type and value again, **Then** no new subscription is created and the existing one is returned unchanged.

---

### User Story 2 - Automatic scheduled collection while running (Priority: P1)

As a user, I want each enabled subscription to check for new papers on its own interval while the plugin is running, so that my vault stays current without manual action.

**Why this priority**: Scheduled collection is the feature's core value; everything downstream (notes, graph) depends on papers arriving.

**Independent Test**: Can be fully tested with a subscription whose interval has elapsed: advance time and confirm a check fires, produces canonical Paper data (by parsing the stubbed provider response into a candidate and promoting it), and updates the subscription's last-checked time.

**Acceptance Scenarios**:

1. **Given** an enabled subscription whose interval has elapsed, **When** the plugin is running, **Then** it checks the provider for new papers with no manual action from the user.
2. **Given** a check completes, **When** it finishes, **Then** the subscription's last-checked time is updated to the moment of that check.
3. **Given** the same paper is found through two different subscriptions, **When** both checks run, **Then** the paper is processed only once (deduplicated by source identifier).

---

### User Story 3 - Catch-up collection across the off period (Priority: P1)

As a user who closes Obsidian overnight or for days, I want the plugin, when I open it again, to find the papers that were published while it was off, so that turning the plugin off never creates a permanent blind spot in my tracking.

**Why this priority**: This is the explicit behavior that replaces background collection. Without it, any time the plugin is off is lost coverage.

**Independent Test**: Can be fully tested by setting a subscription's last-checked time to the past, loading the plugin, and confirming exactly one catch-up search runs per enabled subscription over the window from last-checked to now, producing the papers the (stubbed) provider reports for that window and then advancing last-checked to the moment actually searched through — to now when the window fit within one pass, or (if the stubbed window exceeds the paging cap) only to the newest paper fetched, with the remainder covered on the next pass per FR-026.

**Acceptance Scenarios**:

1. **Given** the plugin has been off and a subscription's last-checked time is in the past, **When** the plugin loads, **Then** a single catch-up search runs for that subscription covering the window from its last-checked time to the current time.
2. **Given** the catch-up search completes, **When** it finishes, **Then** the subscription's last-checked time is advanced to the moment actually searched through — the current time when the whole window fit in one pass, or only to the newest paper fetched when the window exceeded the paging cap (FR-026) — so the same span is never searched twice and any uncovered newer remainder is picked up on the next pass.
3. **Given** the plugin is off, **When** no plugin process is running, **Then** no collection occurs during the off period — collection only resumes as catch-up on the next load.
4. **Given** a disabled subscription, **When** the plugin loads after an off period, **Then** no catch-up search runs for it.

---

### User Story 4 - Provider parsing and citation enrichment (Priority: P2)

As a user relying on collected papers to be complete and trustworthy, I want each provider's response format parsed into the plugin's single canonical paper shape, with citation data clearly marked as confirmed or unconfirmed, so I never mistake an unenriched arXiv paper's placeholder "0 citations" for a real zero.

**Why this priority**: Correct parsing and the `citationsKnown` distinction are what keep every downstream feature (persistence, summarization, graph styling) from silently trusting fabricated data. It matters less than the collection mechanics above but must be right before those features consume this feature's output.

**Independent Test**: Can be fully tested by feeding stubbed arXiv Atom XML and Semantic Scholar JSON responses through parsing and confirming both produce the same canonical `PaperCandidate`/`Paper` shape (001), with `citationsKnown` set correctly in each case.

**Acceptance Scenarios**:

1. **Given** a stubbed arXiv Atom XML response, **When** it is parsed, **Then** it produces a `PaperCandidate` with an unknown citation count and unknown references (never a fabricated 0 or empty list).
2. **Given** a stubbed Semantic Scholar JSON response, **When** it is parsed, **Then** it produces a `PaperCandidate` carrying its actual citation count and references.
3. **Given** a candidate promoted without citation enrichment, **When** it is stored, **Then** its `citationCount` defaults to 0, its `references` default to an empty list, and `citationsKnown` is `false`.
4. **Given** a candidate enriched from a citation-aware provider before promotion, **When** it is stored, **Then** its `citationsKnown` is `true`.

---

### User Story 5 - Backfill historical papers on demand (Priority: P3)

As a user who also wants the foundational literature behind a topic — not just papers published after I subscribed — I want to explicitly trigger, per subscription, a one-off collection of papers going back to a start date I choose, without disturbing the regular forward collection, without duplicates, and without freezing the interface even for a large history.

**Why this priority**: This is an opt-in convenience layered on top of automatic forward collection (US1–3) and parsing (US4); the full discovery/parse/enrich/promote/persist pipeline must already exist for it to reuse. It is never required for the feature's core value and never runs unless the user asks for it.

**Independent Test**: Can be fully tested by taking a subscription whose forward floor (`coveredFrom`) is set to a past instant, calling the backfill request with an older `targetFrom`, and confirming the `[targetFrom, coveredFrom)` window is covered from a stubbed provider oldest-first, that `lastCheckedAt` never changes, and that papers the forward pass already collected are not re-processed.

**Acceptance Scenarios**:

1. **Given** a subscription with a forward floor in the past, **When** the user requests backfill from an earlier start date, **Then** papers in the window from that start date up to the forward floor are collected.
2. **Given** a backfill window larger than the paging cap, **When** backfill runs, **Then** it covers the window across multiple passes (oldest-first, monotonically), resuming from its persisted cursor after a plugin restart, losing no historical paper.
3. **Given** a paper the forward collection already stored, **When** an overlapping backfill encounters it, **Then** it is deduplicated and not re-processed.
4. **Given** a running or completed backfill, **When** it progresses, **Then** the subscription's `lastCheckedAt` is never read or advanced by it.
5. **Given** an in-progress backfill, **When** the subscription is disabled, **Then** backfill pauses (no new pass starts); **When** it is re-enabled, **Then** backfill resumes from its persisted cursor.

---

### User Story 6 - Check an existing subscription now (Priority: P3)

As a user who just heard about new work in a topic I already track, I want to force one of my existing subscriptions to check immediately instead of waiting up to its full interval (6–72 hours), so I can pull in what is out there right now.

**Why this priority**: A manual convenience on top of scheduled collection (US2); the scheduled check machinery it reuses must already exist. The feature is fully functional without it — it only shortens the wait for the next check.

**Independent Test**: Can be fully tested by taking an enabled subscription whose interval has not yet elapsed, invoking the on-demand check, and confirming a check runs immediately over `[lastCheckedAt, now]`, advances `lastCheckedAt` as any check does, and is never run concurrently with a scheduled tick (the in-flight guard blocks overlap).

**Acceptance Scenarios**:

1. **Given** an enabled subscription whose interval has not elapsed, **When** the user triggers an on-demand check, **Then** a check runs immediately without waiting for the next scheduled tick.
2. **Given** an on-demand check is already in flight for a subscription, **When** its scheduled tick becomes due, **Then** the tick skips that subscription (in-flight guard), so it is never checked twice concurrently.

### Edge Cases

- If the external database is temporarily unreachable, the check must not crash; the system retries at the scheduler's next 15-minute tick (not the subscription's own longer check interval, since a failed check leaves it due) and is able to inform the user of the failure — once per failure episode, not on every retry (FR-012a). The subscription's last-checked time is not advanced past a window that was not actually searched.
- If an unusually large number of papers is discovered at once (e.g., right after registering a subscription, or after a long off period), they must be processed sequentially without freezing the interface.
- If a discovered paper is missing required information such as publication year (a *successful* response lacking a year), it is skipped rather than collected, per the hold-back rule in 001 — not treated as a provider failure, and not retried against the same provider. Because the check still succeeds and advances the last-checked time past this paper's window, the skip is permanent for forward collection (the paper won't reappear in a later forward tick); it can only be re-discovered by a manual backfill (FR-033) over its submission time, by when it may have gained a year. This is deliberately unlike missing citation data, which never holds a paper back.
- An arXiv-only paper carries no citation data, so its candidate's citation count and references are unknown. If it is promoted without Semantic Scholar enrichment, it is stored with a citation count of 0 and no references, but with `citationsKnown = false` so it remains distinguishable from a genuinely uncited paper (`citationsKnown = true`, count 0). A later enrichment or manual refresh (005) fills the real values and sets the flag true. This is expected behavior, not a failure.
- Enrichment can fail on a paper that is otherwise complete (has a year): Semantic Scholar is unreachable/rate-limited, or has no record for that paper's arXiv ID (a real but not-yet-indexed paper — see Clarification 2026-07-06, which matches by arXiv ID only). The paper MUST NOT be held back for this — it is promoted and persisted immediately with `citationsKnown = false`, so under windowed collection it never falls out of the search window and is not lost when the last-checked time advances. It is re-enriched later from the persisted store (refresh 005, or a future auto-heal sweep — currently only a deferred idea, not an existing feature), not by rescanning the window.
- Re-enrichment of `citationsKnown = false` papers must terminate: a provider positively reporting "no such paper" for that arXiv ID is a terminal absence and is not retried automatically; transient failures are retried a bounded number of times before being left to manual refresh (005). Neither case blocks or reverses the paper's persistence.
- If the plugin is turned off mid-check, the subscription's last-checked time must not advance past the portion of the window that was actually completed, so the unsearched remainder is picked up on the next load.
- If two subscriptions' catch-up windows overlap and surface the same paper, it is still processed only once.
- If a provider limits how far back a query can reach — catch-up or regular tick — the user is informed that the window could not be fully covered.
- If a subscription is disabled while its check is already running, that check is not aborted and still advances `lastCheckedAt` on success; only checks that have not yet started are prevented by the disable (FR-010).
- If a user registers a subscription whose type and value already match an existing one, no duplicate is created — the existing subscription is returned unchanged, and any newly-supplied label/interval in that request is ignored.
- If summarization is turned off while a specific paper's summary generation is already in flight, the completed-but-now-stale result is discarded and the paper is persisted with the abstract fallback instead, exactly as if summarization had been off from the start of that check.
- If several subscriptions are due at once, they are checked one after another, never in parallel.
- If a single provider entry is too structurally incomplete to build a candidate at all, it is skipped and the rest of the batch still completes.
- If the system clock moves backward past a subscription's last-checked time, that check searches an empty window rather than sending a provider an invalid (reversed) date range, and leaves `lastCheckedAt` unchanged (it is not moved backward to the earlier "now"), so no already-covered span is re-searched once the clock returns to normal.
- If a user attempts to register a subscription with an empty or whitespace-only value, the attempt is rejected and no subscription is created.
- If a window contains more papers than a single check will page through, the oldest papers (by submission date) are fetched first and the last-checked time advances only to the newest one fetched, so the remaining newer papers are collected on the next check rather than skipped — the truncation notice means "more coming next pass," not "papers lost."
- If a check discovers many new papers at once, their citation enrichment is looked up in one batched request (or a few, chunked) against the citation-aware provider, not one request per paper.
- If a user registers a brand-new subscription while the plugin is running, its first check starts immediately rather than waiting for the next scheduled tick; the in-flight guard keeps that immediate check and the next tick from overlapping.
- If a subscription that was disabled for a long time is re-enabled, its next check catches up over the entire disabled period (window from its unchanged last-checked time to now), just like a plugin-was-off catch-up; it does not silently skip that period.
- If a user requests backfill over a history larger than a single pass's paging cap, it is covered oldest-first across successive passes, its cursor persisted so it resumes after a plugin restart; no historical paper is permanently lost.
- If a backfill window overlaps papers the forward collection already stored, each such paper is deduplicated (FR-009) and processed only once — backfill shares the same dedup as forward collection.
- If a backfill request's start date is not older than the subscription's current forward floor, it is a no-op (nothing older to fill); if a further-past start date is requested while a backfill is already in progress, coverage extends downward from that new start date.
- If a subscription is disabled mid-backfill, the backfill pauses (no new pass begins; any pass already running finishes and records its progress) and resumes from its persisted cursor on re-enable; deleting the subscription removes its backfill state along with it.
- If a backfill provider call fails, the cursor is not advanced, the failure is surfaced through the existing notice mechanism (FR-012/FR-014), and the pass is retried on a later tick/load — exactly as a forward check failure is.
- If the arXiv provider cannot reach as far back as a requested backfill start date, the user is informed the window could not be fully covered (FR-014), the same notice a truncated forward window uses.
- If a user triggers an on-demand check on a subscription that already has a check in flight, the manual trigger is coalesced with the in-flight check rather than starting a second concurrent one (shared in-flight guard).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A user MUST be able to register a new subscription by entering its type (keyword / author / arXiv category) and value, with an optional display label (defaulting to the value when omitted); a newly registered subscription receives the default check interval defined in 001 unless the user chooses another allowed interval. Registering a `(type, value)` pair that already exists as a subscription MUST return the existing subscription unchanged rather than creating a duplicate.
- **FR-002**: A user MUST be able to view the list of registered subscriptions and delete, enable/disable, or change the check interval of any individual subscription (per the acceptance rule in 001: an interval outside the five allowed values is rejected and the prior value kept). Changing a subscription's `type`/`value`/`label` after registration is out of scope — tracking a different search term requires deleting and re-registering.
- **FR-003**: While the plugin is running, each enabled subscription MUST automatically check for new papers at its specified interval, with no manual action from the user.
- **FR-004**: When the plugin loads after having been off, it MUST perform a single catch-up search per enabled subscription covering the window from that subscription's last-checked time to the current time, so papers published while the plugin was off are still found.
- **FR-005**: No collection may run while the plugin is off; there is no background process. Collection resumes only as scheduled checks or catch-up searches once the plugin is running again.
- **FR-006**: After any successful check or catch-up search, the subscription's last-checked time MUST be advanced to the moment searched-through, so the same window is never searched twice. It MUST NOT be advanced past a window that failed or was interrupted.
- **FR-007**: Every collected paper MUST be parsed from the provider's response into the canonical Paper shape defined in 001, including title, authors, publication year, citation count, abstract, and source identifier; persisting it as a JSON record + Markdown note is owned by 003.
- **FR-008**: All communication with external databases (arXiv, Semantic Scholar) MUST happen only within this feature; no other feature communicates with external sources directly. Parsing and normalizing each provider's wire format (arXiv Atom XML, Semantic Scholar JSON) into the canonical Paper shape is likewise confined here — no raw provider payload (XML or a provider's own JSON) may be persisted or handed to another feature.
- **FR-009**: If the same paper is discovered through multiple subscriptions or overlapping catch-up windows, it MUST be processed only once, deduplicated by its source identifier.
- **FR-010**: Disabling a subscription MUST immediately stop any new collection caused by it, including catch-up searches on subsequent loads.
- **FR-011**: A discovered paper missing required information (e.g., a successful response with no publication year) MUST be skipped rather than collected, per the 001 hold-back rule, and this MUST be distinguished from a provider-call failure (which retries) — a successful response that genuinely lacks a year is not retried against the same provider. Because a successful check advances `lastCheckedAt` past this paper's window, such a skip is permanent for *forward* collection: the paper falls outside every future forward window and is not re-collected on a later tick. It is not permanently unreachable, however — a manual backfill (FR-033) that re-covers the paper's submission time re-discovers it, and by then the paper may have gained a year (a preprint that was later published, or a second discovery path). This is the one asymmetry with missing *citation* data, which never holds a paper back (FR-016/FR-018): a yearless candidate has no sane default for the year and cannot be promoted at all, so it is skipped instead of stored.
- **FR-012**: If a provider is unreachable or a call fails, the system MUST retry — in practice, on the scheduler's next 15-minute tick (research.md Decision 4), since a failed check leaves `lastCheckedAt` untouched and the subscription remains due until it succeeds; this is not gated behind the subscription's own check interval (6/12/24/48/72h) — MUST NOT advance the last-checked time past the unsearched window, and MUST be able to inform the user of the failure (see FR-012a for repeat-notice suppression).
- **FR-012a**: A repeated failure for the same subscription (e.g., a provider down for hours, retried every 15-minute tick) MUST NOT re-surface a user-facing notice on every retry. A notice fires once when the subscription transitions into a failing state; while it remains failing, subsequent retries MUST NOT notify again until it either succeeds (recovers) or a different failure reason occurs.
- **FR-013**: A large batch of discovered papers MUST be processed sequentially without freezing the interface.
- **FR-014**: If a provider caps how far back a single query can reach — whether during the catch-up pass or a regular scheduled tick — the system MUST inform the user that the requested window could not be fully covered.
- **FR-015**: Collection MUST parse each provider response into a `PaperCandidate` (001) before it becomes a valid `Paper`. Where a provider does not supply a citation count or references (e.g., arXiv), the candidate MUST represent them as *unknown* rather than as 0 or an empty list, so that "unknown" is never conflated with a confirmed zero.
- **FR-016**: A candidate MUST be promoted to a valid `Paper` only when it has a publication year; on promotion, an unknown citation count becomes 0 and unknown references become an empty list, and the paper's `citationsKnown` flag records whether citation data was actually present (see FR-018). Missing citation data MUST NOT hold a candidate back — the publication year is the only hold-back trigger. Collection MUST attempt to enrich each check's candidates from the citation-aware provider (Semantic Scholar) via the batch lookup of FR-027, and normally does so *before* promotion so a confirmed count is available up front for downstream consumers (summarization 004, uncited-node styling 007) — a batch-confirmed 0 is what lets a stored 0 mean "confirmed uncited". Enrichment being always-attempted (FR-027) does not make it a promotion gate, however: when the batch fails or returns no record for a candidate's arXiv ID, that candidate is still promoted and stored (with `citationsKnown = false`) and corrected later by re-enrichment or a manual refresh (005), rather than being withheld. Only the publication year gates promotion; citation enrichment never does.
- **FR-017**: This feature MUST own the per-paper processing pipeline: for each collected paper it enriches (where citation accuracy is needed), then — if summarization (004) is enabled — invokes 004 to generate summary/future-directions text, then hands the finished paper to 003 for a single coordinated persist. It MUST NOT itself implement text generation (004) or file I/O (003); it only sequences them. A summarization failure MUST NOT block persistence — 004's abstract fallback applies and the paper is still saved.
- **FR-018**: Every promoted `Paper` MUST carry a `citationsKnown` boolean (defined in 001): true when its citation count/references came from a citation-aware provider (a 0 then means "confirmed uncited"), false when it was promoted without citation data (a 0 then means "unknown, not confirmed uncited"). Enrichment failure on an otherwise-complete paper (provider unreachable, or no Semantic Scholar record for that paper's arXiv ID — see Clarification 2026-07-06) MUST result in immediate promotion with `citationsKnown = false` — never a hold-back. The persisted store is the source of pending enrichment: refresh (005) — and any future auto-heal sweep, should one ever be built (currently only a deferred idea, `specs-futureworks/010-automatic-citation-refresh`, not part of this or any shipped feature) — MUST target exactly the `citationsKnown = false` papers and MUST NOT rescan the collection window to find them. Any such re-enrichment MUST terminate: a provider positively reporting the paper's absence for that arXiv ID is a terminal state that is not retried automatically, and transient failures are retried a bounded number of times before being left to manual refresh. Consumers that depend on citation status (004, 007) MUST treat a `citationsKnown = false` count of 0 as un-enriched rather than as a genuine zero.
- **FR-019**: When Semantic Scholar enrichment supplies a paper's references/citations, each reference's `sourceId` MUST be normalized to the `arxiv:` scheme (001) whenever the referenced work has a known arXiv ID, and MUST keep a `semanticScholar:`-scheme identifier only when no arXiv ID is available (Clarification 2026-07-05), so that graph edges (006) can connect an enrichment-supplied reference to a paper independently collected via arXiv.
- **FR-020**: A user MAY optionally configure a Semantic Scholar API key in plugin settings; when one is configured, every Semantic Scholar request this feature makes MUST include it. This feature MUST function fully (enrichment still succeeds, still falls back to `citationsKnown = false` on failure) when no key is configured — the key only changes which rate-limit pool a request draws from, never whether enrichment is attempted.
- **FR-021**: The current `summarizationEnabled` setting MUST be read live — freshly per paper processed, at the moment each is used, never a value captured once when the plugin loaded or once when a check began. (A batch can take long enough that a setting changed mid-batch must take effect for later papers in the same batch, not only on the next check.) If summarization is turned off while a specific paper's summary generation is already in flight, this feature MUST re-read the setting after that generation completes and discard the in-flight result if it is now off, falling back to the abstract (004's own fallback), rather than persisting a summary generated after the setting was turned off. The Semantic Scholar API key MUST likewise be read live rather than captured once at plugin load — but, because citation enrichment for a check's papers is looked up in a single batched request (FR-027) rather than per paper, the key is read live once per check, at the moment that check's enrichment batch is issued, not separately for each paper within it.
- **FR-022**: Whenever more than one subscription check would run at overlapping times, the checks MUST run one at a time, sequentially — never concurrently. This covers not only multiple subscriptions becoming due in the same scheduled tick or catch-up pass, but every check-triggering path: a scheduled tick, a catch-up pass, the immediate first check of a newly registered subscription (FR-028), a manual on-demand check (FR-032), and a backfill pass (FR-039). All of them funnel through the one shared sequential path and in-flight guard, so no two checks — regardless of what triggered them — ever issue outbound provider requests at the same time.
- **FR-023**: A single structurally-incomplete provider entry that prevents building a candidate at all (e.g., missing the element a source identifier is built from) MUST be skipped without aborting the rest of that check's batch, distinctly from — but with the same "skip, don't fail the batch" spirit as — the FR-011 publication-year hold-back.
- **FR-024**: If the current time is earlier than a subscription's last-checked time (e.g., a system clock moved backward), the computed search window MUST NOT be sent to a provider as an inverted range; the check MUST instead treat it as an empty window that discovers nothing, and MUST leave `lastCheckedAt` unchanged rather than moving it to the earlier current time. Moving it backward would re-open an already-covered span once the clock returns to normal, searching the same window twice in violation of FR-006; leaving it unchanged means the next check whose current time is again at or after `lastCheckedAt` resumes forward coverage with no overlap and no gap.
- **FR-025**: Registering a subscription whose value is empty or contains only whitespace MUST be rejected; no subscription is created.
- **FR-026**: Every arXiv discovery query MUST request results in explicit `submittedDate` ascending order (never the provider's default relevance ordering). When a single check's window yields more results than the feature's own paging cap and is therefore truncated (FR-014), the subscription's last-checked time MUST advance only to the submission time of the last (newest) paper actually fetched — never to the current time — so that the uncovered newer remainder of that window is collected on a subsequent check rather than permanently skipped. A truncated window MUST NOT cause any paper within it to be permanently lost; it only spreads that window's coverage across more than one check. If the newest fetched paper's submission time cannot be read (a structurally-incomplete entry, per FR-023), the last-checked time MUST instead use the newest fetched paper that does have a readable submission time, or — if none of the fetched papers has one — MUST NOT advance past the window's start; it MUST NEVER be set to an invalid or unreadable value. This no-advance case MUST NOT loop forever: if a truncated window makes no forward progress across successive checks because none of the papers it can fetch has a readable submission time, the check MUST surface the FR-014 "window could not be fully covered" notice and advance `lastCheckedAt` past that stalled prefix (to the current time, or to the window's `to` bound) so the subscription does not re-fetch the same unreadable prefix on every future tick. This is the one bounded exception to the "no paper permanently lost" guarantee: it applies only to entries too structurally incomplete to yield a submission time at all (already unpromotable under FR-023), and trades their loss for scheduler liveness rather than stalling the subscription indefinitely.
- **FR-027**: Citation enrichment for the papers discovered in a check MUST be performed against the citation-aware provider's batch lookup (multiple paper identifiers per request, chunked to the provider's per-request maximum) rather than one request per paper, so that a check surfacing many new papers does not issue one external request per paper. A paper the batch reports no record for is treated identically to the single-paper terminal-absence case (promoted with `citationsKnown = false`, FR-018).
- **FR-028**: Registering a genuinely new subscription (one that did not already exist per FR-001's `(type, value)` idempotency) while the plugin is running MUST begin that subscription's first check immediately, without waiting for the next scheduled tick, reusing the same check path and in-flight guard so the immediate check and the next scheduled tick can never process it concurrently.
- **FR-029**: Re-enabling a previously disabled subscription MUST perform an ordinary catch-up over the window from its (unchanged) last-checked time to the current time — exactly like a plugin-was-off catch-up — so papers published while it was disabled are still collected. Re-enabling MUST NOT reset the last-checked time or shorten the look-back window.
- **FR-030**: A brand-new subscription (one with no prior last-checked time) MUST have its first collection window bounded to the shortest allowed check interval (24 hours) looking back from registration, never further. Registering a subscription therefore cannot flood the vault with arbitrarily old historical papers; reaching further into the past is available only through the explicit, opt-in backfill of FR-033, never as an automatic consequence of registration. (Promotes Clarification 2026-07-05.)
- **FR-031**: arXiv MUST be the sole discovery source for all subscription types (keyword / author / arXiv category); Semantic Scholar MUST be used only to enrich papers already discovered via arXiv with citation data, and MUST NEVER be queried as an independent discovery source. A paper that does not surface through arXiv discovery is therefore out of this feature's reach by design. (Promotes Clarification 2026-07-05.)
- **FR-032**: A user MUST be able to trigger an immediate on-demand check of an existing enabled subscription, running its ordinary `[lastCheckedAt, now]` check right away instead of waiting for its next scheduled tick. This on-demand check MUST reuse the same check path and in-flight guard as a scheduled tick, so it and the next tick can never process the subscription concurrently; it advances `lastCheckedAt` exactly as any check does. This is the existing-subscription counterpart to FR-028's immediate first check of a newly registered subscription.
- **FR-033**: A user MUST be able to manually initiate, per subscription, a one-off backfill of the past window `[targetFrom, coveredFrom)` — where `targetFrom` is a user-specified past instant and `coveredFrom` is the subscription's current backward floor (the oldest instant forward collection has covered). Backfill MUST NOT be initiated automatically on registration; it is strictly opt-in.
- **FR-034**: Backfill MUST reuse forward collection's discovery/parse/enrich/promote/persist pipeline and its dedup (FR-009) unchanged, differing only in the window it searches. The `Paper` records it produces, including `citationsKnown` semantics, MUST be identical to those forward collection produces.
- **FR-035**: Backfill MUST NOT read or advance `lastCheckedAt`. It MUST operate solely on its own backward floor (`coveredFrom`) and progress cursor (`backfillState.cursor`), fully independent of forward scheduling, so a backfill in progress has zero effect on when or over what window forward checks run.
- **FR-036**: Backfill MUST be resumable. When a backfill pass truncates at the paging cap, it MUST advance its cursor only to the covered oldest-first prefix (reusing FR-026's truncation-aware advancement) and persist that cursor, so a window larger than one pass is covered across multiple passes and continues after a plugin restart. No historical paper within the requested window may be permanently lost. On completion (cursor reaches `coveredFrom`), the subscription's `coveredFrom` MUST be lowered to `targetFrom` and the backfill state cleared, so a later request for a still-earlier start chains further down without overlap.
- **FR-037**: Disabling a subscription MUST pause its backfill (no new pass starts; a pass already in flight finishes and records its progress); re-enabling MUST resume from the persisted cursor; deleting the subscription MUST remove its backfill state along with it.
- **FR-038**: A backfill request whose `targetFrom` is not older than the current `coveredFrom` MUST be a no-op (nothing older to fill). A request with an empty, future, or non-date `targetFrom` MUST be rejected. If a further-past `targetFrom` is supplied while a backfill is already in progress, coverage MUST extend downward from the new `targetFrom`.
- **FR-039**: A backfill pass MUST run through the same shared sequential path and in-flight guard as forward checks (FR-022), so a subscription's backfill pass and a forward tick can never run concurrently, and MUST yield to the event loop so it never freezes the interface (FR-013).
- **FR-040**: A backfill provider failure MUST NOT advance the cursor, MUST be surfaced through the existing notice mechanism (FR-012/FR-012a/FR-014), and MUST be retried on a later tick/load — exactly as a forward check failure is handled.

### Key Entities

- **Subscription**: As defined in 001. This feature reads its type/value/interval/last-checked/enabled fields and updates last-checked after each check. It additionally maintains two optional backfill-related fields (an additive 001 extension, following the `semanticScholarApiKey` precedent): `coveredFrom` — the backward floor, the oldest instant this subscription's collection has covered, first recorded at the first forward check as that window's start (registration − 24h) and lowered by backfill — and `backfillState` — present only while a backfill is active, holding the run's `targetFrom` and its progress `cursor`.
- **Backfill Window**: The past time range a backfill pass covers — from `backfillState.cursor` up to `coveredFrom`. Like the Collection Window, it is not persisted as its own entity; it is derived each pass from the subscription's cursor and forward floor. Backfill searches it oldest-first and advances the cursor upward toward `coveredFrom`.
- **Paper / PaperCandidate**: As defined in 001. This feature parses provider responses into a `PaperCandidate` (which may carry an unknown citation count and unknown references when a provider like arXiv supplies none), optionally enriches it from a citation-aware provider, then promotes it to a valid `Paper` — holding back only candidates that lack a publication year (per the 001 rule), and on promotion defaulting an unknown citation count to 0 / unknown references to an empty list while setting the `Paper.citationsKnown` flag (001) to record whether citation data was actually present. `citationsKnown = false` marks a paper promoted without confirmed citations; this feature re-enriches exactly those from the persisted store. Persisting each paper as a JSON record + Markdown note is owned by 003. This feature writes no files.
- **Collection Window**: The time range a given check or catch-up search covers — from the subscription's last-checked time to the moment of the check. Not persisted as its own entity; it is derived each time from the subscription's last-checked time and the current time.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An enabled subscription checks for new papers on schedule while the plugin runs, with zero manual actions from the user.
- **SC-002**: After the plugin has been off, opening it results in exactly one catch-up search per enabled subscription per load, covering the off-period window, and papers published during that window are collected. When the off-period window exceeds the paging cap, that single per-load search covers its oldest-first prefix and the remainder is covered across successive passes (SC-012), rather than all of it necessarily arriving in the first search.
- **SC-003**: No collection activity occurs while the plugin is off (0 external calls made by any background process).
- **SC-004**: If the same paper is found through multiple subscriptions or overlapping windows, it is processed exactly once.
- **SC-005**: Disabling a subscription results in zero further collection attributable to it, including on later loads.
- **SC-006**: 100% of collected papers are represented as canonical Paper data parsed from provider responses; no other feature makes external calls.
- **SC-007**: A paper collected from a citation-less provider (arXiv) without enrichment is stored with a citation count of 0, empty references, and `citationsKnown = false` — never a fabricated non-zero value and never conflated with a confirmed zero; after enrichment or a manual refresh (005) it reflects the citation-aware provider's actual values with `citationsKnown = true`.
- **SC-008**: No paper is lost to enrichment failure: a paper whose enrichment fails is still persisted on the same pass (with `citationsKnown = false`), and every such paper is reachable for later re-enrichment directly from the store, with zero rescans of the collection window required to find it.
- **SC-009**: Registering a `(type, value)` pair that already exists never results in two subscriptions sharing the same type and value — 100% of such attempts return the pre-existing subscription instead.
- **SC-010**: A paper whose summary generation was in flight when summarization was turned off is never persisted with that stale summary — 100% of such papers fall back to the abstract instead.
- **SC-011**: Zero registration attempts with an empty or whitespace-only value ever result in a created subscription.
- **SC-012**: No paper in a window that exceeds the paging cap is permanently lost: a truncated window is fully covered across successive checks (each advancing the last-checked time only to the newest paper actually fetched), and repeated checking of such a window makes monotonic forward progress rather than re-fetching the same oldest papers indefinitely.
- **SC-013**: Enriching N discovered papers issues at most ⌈N / (provider batch maximum)⌉ external enrichment requests — for a typical check, exactly one — never N single-paper requests.
- **SC-014**: A genuinely new subscription registered while the plugin runs has its first check begin without waiting for the next scheduled tick, and is never processed concurrently by that immediate check and the following tick.
- **SC-015**: A manually triggered backfill collects the papers from a user-chosen start date up to the subscription's forward floor (`coveredFrom`), with zero duplicates against what forward collection already stored.
- **SC-016**: No historical paper is lost to a backfill window larger than the paging cap: such a window is covered across successive passes that advance monotonically and resume after a plugin restart.
- **SC-017**: Backfill never changes a subscription's `lastCheckedAt` — a backfill run has zero effect on forward scheduling (0 forward checks re-timed or re-windowed by it).
- **SC-018**: Registering a subscription still collects only the most recent 24-hour window — 100% of registrations stay bounded to that window, with older papers arriving only via an explicit backfill, never automatically.
- **SC-019**: A manually triggered on-demand check of an existing subscription begins without waiting for the next scheduled tick, and is never run concurrently with that subscription's scheduled tick (the in-flight guard blocks overlap).

## Assumptions

- "The plugin was off" and "the plugin is loading" are observable to this feature via the plugin lifecycle owned by 008; this feature only needs the last-checked time (from 001) and the current time to compute the catch-up window.
- Providers accept a date/time-bounded query (or an equivalent that lets results be filtered to the catch-up window); where a provider does not, the feature filters returned results to the window itself.
- The exact retry counts, page sizes, and inter-request delays (pinned in `research.md`) are implementation-level tuning, not product-level requirements; this specification requires only that failures retry on the scheduler's next tick, are surfaceable to the user without repeat-notice spam (FR-012/FR-012a), and that a large result set is paged/bounded rather than fetched without limit (FR-013/FR-014).
- Providers differ in both wire format and coverage: arXiv returns Atom XML and supplies no citation data; Semantic Scholar returns JSON and supplies citation data. This feature parses and normalizes both into the plugin's single canonical Paper shape (001). The internal representation the rest of the plugin uses — a JSON record plus a Markdown note (003) — is the plugin's own normalized schema, distinct from and never a passthrough of any provider's wire payload.
- The same underlying paper appearing under different `sourceId`s across providers (out of scope for cross-provider identity per 001) is accepted as a possible duplicate node; reconciling such duplicates is left to a future feature.

## Out of Scope

- Implementing 003 (persistence) or 004 (summarization) themselves. This feature only sequences calls to them through narrow function-call hooks (FR-017); until 003/004 exist, those hooks are satisfied by no-op stub implementations. Swapping the stubs for 003/004's real implementations, once those features ship, is that future work's task, not this one's — `runSubscriptionCheck`/`runCollectionPass`'s own logic does not change when that swap happens.
- Automatically re-enriching already-persisted papers whose `citationsKnown` is `false` on any cadence of this feature's own. Re-enrichment of such papers is either a manual action (005) or a deferred future idea (`specs-futureworks/010-automatic-citation-refresh`), never something this feature initiates unprompted outside its normal collection window.
- Reconciling the same underlying paper collected under two different providers' `sourceId` schemes (see Assumptions above; owned by 001's scope boundary, not extended here).
- Any UI for registering/listing/managing subscriptions, for triggering a backfill (FR-033) or an on-demand check (FR-032), or for surfacing collection-success feedback ("N new papers collected"). This feature exposes only the underlying `subscriptionStore.ts`/scheduler operations; the settings-screen UI and any user-facing controls or success notices that call them are 008's responsibility. (This feature still owns the *failure*/incomplete-window notices of FR-012/FR-014, which are part of collection correctness, not a UI convenience.)
- Limiting the ongoing volume of forward collection (e.g. per-check paper caps, minimum-citation filters, or narrowing filters on a broad category subscription). The 24-hour first-window bound (FR-030) caps only the *initial* registration burst; steady-state forward collection remains unbounded by design (FR-026 guarantees a large window is covered in full across passes, not throttled). Throttling steady-state intake is deferred to a future feature (`specs-futureworks/011-collection-volume-control`) pending evidence that real usage hits the problem; it is deliberately not addressed here.
